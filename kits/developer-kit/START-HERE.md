# 从这里开始

导出对象：开发治理能力包
导出时间：2026-10-14

## 这个包能做什么

- 帮助 AI 在新项目启动时补齐项目结构、协作规则、风险边界和基础文档。
- 帮助 AI 接手已有项目，先理解目录、模块、依赖、运行方式和变更风险。
- 把产品需求转换成架构影响、模块边界、实现计划、测试验证和文档同步。
- 在代码实现前判断影响范围和风险等级，避免盲目改动。
- 在代码实现前做最小必要变更判断，避免过度设计、过早抽象和不必要依赖。
- 支持代码评审、架构决策记录、依赖与技术债治理、环境配置治理、发布回滚和 AI 协作复盘。

## 什么时候使用这个包

当用户输入包含以下意图时，优先使用本能力包：

- 新项目启动。
- 已有项目接手。
- 需求进入开发。
- 架构影响分析。
- 模块边界划分。
- 报错、白屏、测试失败、性能异常或线上问题定位。
- 数据/API/状态契约设计。
- 登录、权限、安全、敏感数据、密钥、上传下载或支付相关开发。
- 变更风险判断。
- 影响范围分析。
- 代码实现。
- 最小必要变更、少写代码、反过度设计、YAGNI、Ponytail 类任务。
- 测试与验收。
- 文档同步。
- 代码评审。
- 架构决策记录。
- 依赖和技术债治理。
- 环境变量、配置和密钥治理。
- 发布、回滚和上线前检查。
- AI 协作复盘。

## 与团队总调度的关系

如果外部项目中同时存在 `team-orchestration-kit`，产品、UI、开发、测试相关任务默认先由 `team-orchestration-kit` 接管。

本包直接接管的情况：

- 项目没有 `team-orchestration-kit`。
- 用户明确指定只使用 `developer-kit`。
- `team-orchestration-kit` 已判断这是纯开发任务，并转交给本包。

## 一句话启动

在新项目或新 AI 对话里，直接复制下面这句话：

```text
请只参考 developer-kit/ 下的文件工作。请先阅读 developer-kit/README.md、developer-kit/usage-guide.md 和 developer-kit/workflows/developer/developer-kit-workflow.md。我的开发任务是：{写下你的任务}。请先判断任务类型，再说明会使用哪个 workflow、template 和 scorecard，然后继续执行。
```

## 更短版本

如果只是快速启动，可以说：

```text
请使用 developer-kit 协助我处理这个开发任务：{写下你的任务}
```

```text

```

## 执行顺序

1. 先判断任务类型和风险等级。
2. 再选择对应 workflow。
3. 再选择对应 template。
4. 执行前说明会读取、修改和验证哪些文件。
5. 如果进入代码实现，先检查项目是否已有设计规范、组件规范、交互规范、代码规范、测试规范和 AI 协作规则。
6. 进入代码实现前，先做最小必要变更判断。
7. 执行后使用对应 scorecard 检查。
8. 如果涉及高风险改动，先说明风险和确认点。


## 开发全链路原则

developer-kit 不应把“命中某个工作流”当成任务结束。

当用户提出一个开发需求时，应默认按完整开发链路判断后续阶段：

```text
需求理解
-> 是否确认进入开发
-> 项目理解
-> 功能整体规划
-> 数据/API/状态契约检查
-> 安全与权限检查
-> 风险和影响范围确认
-> 最小必要变更判断
-> 代码实现
-> 测试验证
-> 文档同步
-> 代码评审
-> 发布或复盘判断
```

不是每个任务都必须完整执行所有阶段，但跳过任何阶段都要说明理由。

进入代码实现前，必须先形成整体功能规划，说明：

- 本次要实现什么。
- 本次不做什么。
- 会影响哪些模块、文件、接口、数据和配置。
- 功能拆分和实现顺序是什么。
- 项目已有的设计规范、组件规范、代码规范、测试规范和 AI 协作规则是什么。
- 模块之间如何协作。
- 如何验证。
- 哪些问题需要用户确认。

进入代码实现前，还必须先检查项目规范来源：

```text
设计规范 / 组件规范 / 交互规范 / 视觉规范
代码风格 / 架构约束 / 目录约定 / 命名规范
测试规范 / 文档规范 / AI 协作规则
```

如果项目存在相关文件，例如 `AGENTS.md`、`AI-WORKFLOW-RULES.md`、`.cursor/rules/`、`docs/design-system.md`、`docs/development-standard.md`、`docs/testing.md`、`.editorconfig`、`.prettierrc`、`.eslintrc`、`biome.json`、`ruff.toml` 等，应先阅读并遵守。

如果没有找到规范，应说明缺失项，并根据任务风险决定：

- 低风险：从现有代码和目录习惯中归纳临时约定。
- 中高风险：先向用户确认，或先补充最小项目规范。
- UI、组件、交互和视觉类改动：没有明确规范时不要直接自作主张，应先列出假设或询问用户。

如果任务属于以下情况，不能直接进入实现：

- 报错、白屏、测试失败、性能异常：先使用 `issue-diagnosis-workflow.md` 定位问题。
- 接口字段、数据结构、状态归属、缓存、错误处理不清：先使用 `data-api-contract-workflow.md` 明确契约。
- 登录、鉴权、角色权限、敏感数据、密钥、上传下载、支付、删除或批量操作：先使用 `security-permission-workflow.md` 检查安全和权限。
- 执行过程中发现需要插入、回退、跳过或暂停确认：参考 `workflow-orchestration-guide.md`。

进入代码实现前，还必须使用最小必要变更判断：

```text
workflows/developer/minimal-change-governance-workflow.md
templates/developer/minimal-change-governance-template.md
scorecards/minimal-change-governance-scorecard.md
```

必须回答：

- 这个需求是否真的需要新增代码。
- 是否可以复用项目已有能力。
- 是否可以使用平台能力、标准库或框架原生能力。
- 是否可以使用已安装依赖，而不是新增依赖。
- 如果必须新增代码，最小完整方案是什么。
- 本次明确不做哪些额外功能、配置、抽象、包装器或未来扩展。
- 哪些安全、校验、错误处理、可访问性和测试不能省略。

中高风险任务进入实现前，还必须拆成开发任务列表：

```text
开发任务列表
-> 当前任务
-> 当前任务验证
-> 是否进入下一条
-> 最终总体验证
```

执行时一次只处理一条任务，不要多条任务混在一起大范围修改。

遇到需求不清、风险较高、方案不唯一、验收标准不明确或可能扩大范围时，先主动询问用户，不要自作主张。

## 外部项目输出目录策略

当本能力包在其他项目中使用，并且用户要求把分析、方案或报告保存为文件时，必须先判断当前项目是否已有统一文档目录。

优先级如下：

1. 如果用户明确指定输出目录，使用用户指定目录。
2. 如果项目已有统一文档目录，优先使用该目录，例如 `docs/`、`documents/`、`工程文档/`、`技术文档/`。
3. 如果项目已有明确的开发文档目录，优先使用该目录，例如 `docs/dev/`、`docs/engineering/`、`technical-docs/`。
4. 如果没有任何合适目录，再在项目根目录创建 `docs/`。

不要在外部项目中默认创建或使用 WorkflowProject 内部目录，例如：

```text
{目标文档目录}/
12-projects/
```

如果任务是代码实现，应优先修改项目真实代码，并在最终回复中说明修改文件、验证结果和剩余风险。

## 长期迭代记忆管理

如果 developer-kit 在同一个外部项目中持续使用，建议维护项目记忆摘要，避免每次让 AI 读取大量历史开发记录。

优先使用项目已有的记忆或规则文件，例如：

```text
AGENTS.md
AI-WORKFLOW-RULES.md
docs/project-memory.md
docs/ai-context.md
```

如果没有合适文件，并且用户希望保存长期上下文，则在已有文档目录中创建：

```text
docs/ai-memory-summary.md
```

每次开发任务结束时，如果产生新的关键结论、架构决策、模块边界变化、风险、验证结果、待处理任务或下一步，应更新该摘要。

如果需要整理长期历史，使用：

```text
workflows/common/iteration-memory-management-workflow.md
templates/common/iteration-memory-summary-template.md
```

## 任务结束标准

任务结束前必须说明：

- 当前阶段是否完成。
- 是否已经进入或不进入下一阶段。
- 如果停止，停止原因是什么。
- 如果实现了代码，验证结果是什么。
- 如果没有验证，原因是什么。
- 是否需要同步文档。
- 是否需要代码评审。
- 是否需要发布或回滚判断。
- 是否有需要用户确认的遗留问题。
- 是否需要更新项目记忆摘要。

如果这些信息没有说明完整，不应直接宣称任务完成。

## 使用原则

- 不确定做什么时，先走开发总入口。
- 已经明确任务时，直接指定对应工作流。
- 不要用文档限制 Codex 或 Cursor 的实现能力，文档负责约束目标、边界、风险和验收。
- 不要把单个细分工作流当作结束点，必须判断后续阶段。
- 进入实现前必须有整体功能规划。
- 进入实现前必须检查并遵守项目已有设计、开发、测试和 AI 协作规范。
- 进入实现前必须做最小必要变更判断，优先不写、复用、平台能力、标准库和已安装依赖。
- 中高风险实现前必须有开发任务列表。
- 实现时必须逐条执行、逐条验证。
- 信息不明确或风险较高时主动询问用户。
- 对已有项目改动前，先理解项目结构和用户已有改动。
- 高风险变更先做影响分析和回滚判断。
- 生成结果后，用对应评分表检查。
- 不需要理解原 WorkflowProject。
