# 测试与验收工作流

## 目的

在代码实现完成后，帮助 AI 根据变更范围和风险等级制定并执行合适的验证方案。

本工作流重点解决：

1. 改完代码后应该验证什么。
2. 哪些测试必须运行，哪些测试可以说明未运行原因。
3. 如何设计手动验收步骤。
4. 如何判断是否需要回归测试。
5. 如何记录验证失败、未验证内容和剩余风险。

一句话：

```text
测试与验收 = 用证据证明这次变更可以交付。
```

## 适用场景

适用于：

- 代码实现已经完成。
- 需要确认变更是否满足需求。
- 需要运行测试、构建、类型检查或 lint。
- 需要给用户可复现的手动验收步骤。
- 需要记录未验证内容和风险。

不适用于：

- 还没有进入代码实现。
- 需求、风险或影响范围尚未明确。
- 用户只要求做只读分析。

## 输入要求

至少需要：

- 变更目标。
- 实现交付说明或修改文件清单。

建议同时提供：

- 影响范围分析报告。
- 风险评估报告。
- 验收标准。
- 项目测试命令。
- 用户希望重点验证的场景。

## 执行原则

### 1. 按风险选择验证强度

| 风险等级 | 验证要求 |
| --- | --- |
| 低风险 | 局部验证，必要时运行相关测试或构建。 |
| 中风险 | 运行相关自动测试，并补充手动验收。 |
| 高风险 | 运行相关测试、构建、回归检查，并列出未覆盖风险。 |
| 危险变更 | 需要人工确认验证计划，不能只靠 AI 自行判断。 |

### 2. 验证必须对应影响范围

验证不能只写“已测试”，必须说明测试覆盖了哪些影响点。

### 3. 失败不能被隐藏

测试失败时必须说明：

```text
失败命令
失败现象
可能原因
已尝试修复
是否仍阻塞交付
```

### 4. 未验证内容必须显式记录

无法运行、无法模拟、依赖外部环境或需要人工操作的内容，必须写入未验证清单。

### 5. 验收步骤应可复现

手动验收应说明：

```text
前置条件
操作步骤
预期结果
异常检查
```

## 执行步骤

### 第 1 步：读取变更和影响范围

确认：

- 修改了哪些文件。
- 影响哪些模块。
- 风险等级。
- 验收标准。
- 需要覆盖的关键路径。

产出：验证目标摘要。

### 第 2 步：制定验证计划

选择验证类型：

- 格式检查。
- 类型检查。
- 单元测试。
- 集成测试。
- 端到端测试。
- 构建验证。
- 手动验收。
- 回归检查。

产出：验证计划。

### 第 3 步：执行自动验证

按项目实际命令执行：

```text
lint
typecheck
test
build
```

如果命令不存在或无法运行，应记录原因。

产出：自动验证结果。

### 第 4 步：设计手动验收

针对用户可观察行为，输出手动验收步骤：

```text
前置条件
操作步骤
预期结果
异常场景
回归点
```

产出：手动验收清单。

### 第 5 步：处理验证失败

如果验证失败：

- 判断是否由本次变更引起。
- 能修复则修复后重跑。
- 不能修复则说明阻塞原因。
- 不得把失败验证写成通过。

产出：失败处理记录。

### 第 6 步：输出测试与验收报告

报告必须包含：

```text
验证目标
验证计划
已运行验证
验证结果
手动验收步骤
未验证内容
失败或风险
是否建议交付
```

```md
## 手动验收步骤

| 内容 | 原因 | 风险 |
| --- | --- | --- |

## 是否建议交付

```

## 快速启动话术

```text
请参考 04-workflows/developer/testing-verification-workflow.md，
基于本次代码变更，帮我做测试与验收。

请先根据修改文件和影响范围制定验证计划，再运行可执行的测试/构建命令，并输出测试与验收报告。

如果有无法验证的内容，请明确说明原因和风险。
```

## 质量要求

- 必须说明验证目标。
- 必须说明测试命令或验证方式。
- 必须记录验证结果。
- 失败不能写成通过。
- 无法验证必须说明原因。
- 必须给出手动验收步骤。
- 必须说明是否建议交付。
