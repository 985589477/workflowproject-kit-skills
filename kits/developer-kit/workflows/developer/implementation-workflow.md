# 代码实现执行工作流

## 目的

在影响范围、风险等级和模块边界已经明确后，指导 AI 稳定完成代码修改。

本工作流重点解决：

1. AI 如何在不扩大范围的情况下实现需求。
2. 如何保护用户已有改动。
3. 如何按模块边界修改代码。
4. 如何在实现前确认项目设计规范、开发规范和测试规范。
5. 如何在实现前判断最小必要变更，避免过度设计。
6. 如何把实现拆成可逐条执行的任务列表。
7. 如何逐条实现、逐条验证，避免一次性大范围修改。
8. 如何同步测试和文档。
9. 如何在实现过程中发现问题并及时停下来确认。
10. 如何输出清晰的交付说明。

一句话：

```text
代码实现执行 = 按已确认的影响范围小步修改、及时验证、清楚交付。
```

## 适用场景

适用于：

- 影响范围已经清楚。
- 风险等级已经明确。
- 模块边界已经清楚。
- 用户已经确认可以进入实现。
- 需要 AI 修改代码、配置、测试或文档。

不适用于：

- 需求仍不清楚。
- 模块边界不清楚。
- 高风险变更尚未获得用户确认。
- 危险变更尚未明确授权。

这些情况应先回到前置工作流。

## 输入要求

至少需要：

- 变更目标。
- 影响范围分析。

建议同时提供：

- 变更风险评估报告。
- 模块边界分析报告。
- 相关文件路径。
- 测试命令。
- 用户明确禁止修改的范围。
- 验收标准。
- 项目设计规范、开发规范、测试规范或 AI 协作规则。

## 执行原则

### 1. 先保护现场

修改前应查看工作区状态，识别已有改动。

如果发现与本任务无关的用户改动：

- 不回退。
- 不覆盖。
- 不整理。
- 只在必要时绕开。

### 2. 严格控制范围

只修改与本次任务相关的文件。

不要顺手重构、顺手改风格、顺手清理无关代码。

### 3. 先遵守项目规范

实现前必须确认并遵守项目已有规范：

- UI 设计规范。
- 组件规范。
- 交互规范。
- 视觉规范。
- 代码风格。
- 架构约束。
- 目录约定。
- 命名规范。
- 测试规范。
- AI 协作规则。

如果规范缺失，不要自行创造大范围新规范。应优先遵守现有代码模式，并说明默认假设。

如果本次涉及 UI、组件、交互或视觉变化，但缺少对应规范，应先向用户确认。

### 4. 小步实现

优先按以下顺序推进：

```text
读相关文件 -> 确认实现点 -> 小范围修改 -> 局部验证 -> 补测试/文档 -> 总体验证
```

### 4.1 最小必要变更

实现前必须先判断：

```text
是否真的需要做
-> 是否可复用项目已有能力
-> 是否可用平台或标准库
-> 是否可用已安装依赖
-> 是否能用清晰的一行完成
-> 最小新增代码
```

不要为了“以后可能需要”新增抽象、包装器、配置项、未使用参数、依赖或大范围重构。

不要为了少写而削减安全、权限、边界校验、防止数据丢失的错误处理、可访问性、用户明确要求或必要测试。

### 5. 逐条执行

中高风险任务必须先拆成开发任务列表。

执行时一次只处理一条任务：

```text
选择当前任务
-> 修改当前任务需要的最小文件集合
-> 运行当前任务对应验证
-> 记录结果和风险
-> 判断是否进入下一条任务
```

不要在未完成当前任务验证前，提前跨到下一条任务。

### 6. 发现风险及时停下

实现过程中如果发现：

- 实际影响范围超过预期。
- 需要改数据结构。
- 需要改权限、登录、支付、生产配置。
- 需要大范围重构。
- 需求与现有设计冲突。
- 项目规范缺失，且会影响 UI、组件、交互、架构或测试策略。
- 发现本次实现会违反已有规范。

应停止继续扩大修改，并向用户说明。

### 7. 验证和交付同样重要

实现完成后必须说明：

```text
改了什么
为什么这样改
验证了什么
没验证什么
剩余风险
后续建议
```

## 执行步骤

### 第 1 步：读取执行输入

确认：

- 变更目标。
- 影响范围。
- 风险等级。
- 模块边界。
- 验收标准。
- 禁止修改范围。
- 项目规范来源。

产出：实现前确认摘要。

### 第 2 步：检查工作区状态

检查是否存在未提交或用户已有改动。

处理原则：

- 只识别，不回退。
- 涉及同一文件时谨慎合并。
- 无关文件不动。
- 如果已有改动导致无法安全修改，先说明阻塞。

产出：工作区状态摘要。

### 第 3 步：读取相关文件

基于影响范围读取：

- 确定影响文件。
- 关键调用链文件。
- 相关测试文件。
- 相关配置或文档。

产出：实现上下文摘要。

### 第 4 步：检查项目规范

检查并输出：

```md
| 规范类型 | 是否存在 | 位置 | 本次如何遵守 | 缺失处理 |
| --- | --- | --- | --- | --- |
| UI 设计规范 | 是 / 否 / 不适用 |  |  |  |
| 组件规范 | 是 / 否 / 不适用 |  |  |  |
| 交互规范 | 是 / 否 / 不适用 |  |  |  |
| 代码风格 | 是 / 否 / 不适用 |  |  |  |
| 架构约束 | 是 / 否 / 不适用 |  |  |  |
| 目录约定 | 是 / 否 / 不适用 |  |  |  |
| 命名规范 | 是 / 否 / 不适用 |  |  |  |
| 测试规范 | 是 / 否 / 不适用 |  |  |  |
| AI 协作规则 | 是 / 否 / 不适用 |  |  |  |
```

如果关键规范缺失，应说明影响和默认假设。

产出：项目规范检查。

### 第 5 步：最小必要变更判断

输出：

```text
最小必要变更判断：
- 是否真的需要做：
- 可复用能力：
- 平台/标准库能力：
- 是否需要新增依赖：
- 推荐方案：
- 明确不做：
- 不能省略的安全/校验/测试：
- 剩余风险：
```

如果判断结果是“不应实现”或“需要用户确认”，不要继续进入代码修改。

产出：最小必要变更判断。

### 第 6 步：制定开发任务列表

根据风险等级决定任务拆解粒度：

| 风险 | 计划要求 |
| --- | --- |
| 低风险 | 可以使用轻量任务列表，至少说明当前任务和验证方式。 |
| 中风险 | 必须列出开发任务列表、影响文件、验收标准和验证方式。 |
| 高风险 | 必须列出开发任务列表，并等待用户确认后逐条执行。 |
| 危险变更 | 默认不执行。 |

开发任务列表格式：

```md
| 序号 | 任务 | 目标 | 影响文件或模块 | 前置依赖 | 验收标准 | 验证方式 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 |  |  |  |  |  |  | 待执行 |
```

产出：开发任务列表。

### 第 7 步：逐条执行代码修改

每一条任务执行时遵守：

- 优先复用现有模式。
- 优先使用项目已有能力、平台能力、标准库或已安装依赖。
- 不引入不必要依赖。
- 不新增没人要求的抽象、配置、包装器或扩展点。
- 不破坏模块边界。
- 不扩大影响范围。
- 不违反项目规范。
- 不覆盖用户无关改动。
- 保持命名、风格和结构一致。
- 本条任务未验证前，不开始下一条任务。

每条任务输出：

```text
当前执行任务：任务 {序号} - {任务名}
本次只改动：{文件或模块}
验证方式：{命令或手动检查}
完成结果：{完成 / 未完成 / 阻塞}
是否进入下一条：{是 / 否，原因}
```

产出：代码变更。

### 第 8 步：逐条验证和记录

每条任务完成后，立即验证：

- 本条任务的验收标准是否满足。
- 本条任务是否引入新的影响范围。
- 是否需要更新任务列表。
- 是否出现阻塞或需要用户确认。

产出：逐条验证记录。

### 第 9 步：补充测试和文档

根据影响范围补充：

- 单元测试。
- 集成测试。
- 端到端测试。
- README。
- API 文档。
- 架构或模块文档。
- 变更说明。

产出：测试和文档变更。

### 第 10 步：执行总体验证

按项目实际情况运行：

- 格式检查。
- 类型检查。
- 单元测试。
- 构建。
- 手动验证说明。

如果无法运行，应说明原因。

产出：验证结果。

### 第 11 步：输出交付说明

交付说明必须包含：

```text
变更摘要
开发任务列表
项目规范检查
最小必要变更判断
逐条执行记录
修改文件
验证结果
未验证内容
风险和注意事项
后续建议
```

```md
| 文件 | 修改内容 | 原因 |
| --- | --- | --- |

| 命令或方式 | 结果 |

## 未验证内容

```

## 快速启动话术

```text
请参考 04-workflows/developer/implementation-workflow.md，
基于已确认的影响范围和风险评估，开始实现这个变更。

变更目标：
【粘贴需求或变更说明】

请先检查工作区状态，保护已有用户改动，然后把实现拆成开发任务列表，按任务逐条实现、逐条验证。每完成一条任务后说明是否进入下一条，完成后运行总体验证，并输出实现交付说明。
```

## 质量要求

- 修改前必须检查相关上下文。
- 不得覆盖用户已有无关改动。
- 不得扩大影响范围。
- 不得引入不必要依赖、抽象和未来扩展。
- 必须遵守模块边界。
- 必须说明验证结果。
- 不能运行的验证必须说明原因。
- 交付说明必须清楚列出修改文件和剩余风险。
