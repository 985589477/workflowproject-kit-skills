# 项目治理标准

## 目的

本标准约束 AI 在真实项目中进行长期协作开发时，如何检查和维护项目治理基础。

## 权威优先级

当不同文件出现冲突时，默认按以下顺序判断：

1. 用户当前明确说明。
2. 真实项目中的安全、部署、代码和架构规则。
3. 真实项目中的架构、模块、设计和任务文档。
4. 当前项目的 `AGENTS.md`、`AI-WORKFLOW-RULES.md` 或工具规则。
5. 已安装的通用 Skill 和角色能力包。
6. WorkflowProject 的通用建议。

通用角色包不能覆盖真实项目已经确认的事实和规则。

## 必查治理对象

进入中等及以上复杂度的开发前，必须检查：

| 治理对象 | 最少需要知道什么 |
| --- | --- |
| 项目入口 | 项目目标、目标平台、技术栈、启动方式、验证方式 |
| 技术基线 | 主要语言、框架及版本、运行时、包管理、构建部署和测试方案 |
| 架构 | 主要层次、数据流、关键依赖、风险区域 |
| 模块 | 职责、输入、输出、依赖、禁止承担的职责 |
| 设计 | 颜色、字体、组件、状态、布局、适配和无障碍要求 |
| 任务 | 当前目标、依赖、验收标准、验证方式和状态 |
| 记忆 | 当前决策、风险、阻塞、已完成内容和下一步 |

## 缺口处理

发现缺少治理材料时，按以下顺序处理：

1. 说明缺失项以及不补齐的风险。
2. 区分可以从项目事实推断的内容和必须询问用户的内容。
3. 提供最小补齐方案和完整补齐方案。
4. 对高风险或不可逆内容等待用户确认。
5. 将确认后的内容写入对应项目文档。

如果是新项目或新模块，技术基线缺失属于必须问询的缺口。AI 应先询问用户，或提供 2-3 个候选方案供用户选择；不能把默认技术偏好直接写成项目决定。

不得因为存在 `developer-kit` 或其他通用能力包，就假设当前项目已经具备架构和设计规范。

## 任务执行要求

中等及以上复杂度的任务必须有任务列表。每条任务至少包含：

```text
任务目标
影响模块或文件
前置依赖
验收标准
验证方式
当前状态
阻塞和备注
```

执行规则：

```text
选择一条任务
-> 完成最小变更
-> 运行对应验证
-> 记录结果
-> 判断是否进入下一条
```

## 角色调用要求

角色是按需调用的专业能力，不是固定流水线。

- 需求问题调用产品能力。
- 设计和适配问题调用 UI 能力。
- 架构和代码问题调用开发能力。
- 质量和验收问题调用测试能力。
- 跨角色任务由团队总调度先判断。

没有必要时不得为了流程完整而调用角色。

## 完成条件

任务结束前至少说明：

- 使用了哪些事实文档。
- 哪些架构、模块或设计文档发生变化。
- 哪些任务已完成，哪些任务未完成。
- 验证执行情况和未覆盖风险。
- 是否需要更新项目记忆。
- 是否可以进入下一阶段。
