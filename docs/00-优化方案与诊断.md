# workflowproject-kit 优化方案 v2

> 目标：把 kit 从「文档库」改成「**会触发、会拦截**的执行系统」。
> 全部内容已按你仓库 `$REPO` 的既有布局产出，可直接拷入并提交。

---

## 一、诊断（实测，不是印象）

| 指标 | 实测 | 问题 |
|---|---|---|
| kit 总内容 | **27,488 行** md / 314 文件 / 1.5MB | — |
| 一次真实任务实际读到的 | **293 行 = 1.1%** | 最详细的内容永远读不到 |
| 6 个能力包有触发面的 | **1 / 6**（且那 1 个是另一份拷贝） | 5 个能力包在目录里不存在 |
| 全仓 `守卫\|门禁测试` 命中 | **0** | 规范全是提示词，没有"违反就红" |

**三个失效机制：**

- **M1 触发面缺失**：harness 只扫一层 `skills/*/SKILL.md`。你的 6 个能力包嵌在
  `workflowproject-kit/kits/` **深度 3**，扫不到。经核对，**它们 6 个的 frontmatter 全部合法**，
  只是位置不对。目录里出现的 `product-manager-kit` 来自 `~/.codex/skills/` 那份**不同的拷贝**。
- **M2 成本结构**：入口(108) → 子包 SKILL.md(19–84) → START-HERE(204–354) + README +
  usage-guide(215–276) + workflows(209–982)。实测**停在第 2 跳**，982 行的
  `developer-kit-workflow.md` 一次没打开。
- **M3 无强制**：kit 有门禁（状态行、问询门禁）但**全在提示词层面**。真正可靠的三样东西
  （架构守卫测试、契约快照、golden 文件）全部来自 ponytail 的"留一个可运行检查"，kit 一条都没要求。

**一个反向证据**：真正起作用的 4 条规则（生命周期 / 子 Agent 分流门禁 / 问询门禁 / 输出位置）
**全在那 108 行入口里**。→ 入口就能承担全部约束力，问题只是入口装得太少、
又用"必读链条"把细节推到了读不到的地方。

## 二、总纲：三个机制替代「必读」

| 机制 | 解决 | 手段 |
|---|---|---|
| **触发** | M1 M2 | 能力包独立注册（1 跳路由）+ 入口压成门禁表 + 项目 `AGENTS.md` 活状态被 harness 每轮回灌 |
| **强制** | M3 | 门禁产出**可运行检查**，`check_gates.py` 校验，提交前拦截 |
| **检索** | M2 | 不再"必读"；门禁表直接指向**那一个**要读的文件 |

**核心洞察**：`ponytail` 100% 生效是因为它在**系统提示里内联**；`AGENTS.md` 持续生效是因为
harness 每轮**回灌**它。**注入 > 检索。** 所以要"让规范触发"，最有效的手段是**缩短到注入路径**，
而不是把文档写得更全。

**因此本方案刻意不做 `INDEX.md`**：批 1 的符号链接已经让 harness 目录能直接路由到对应能力包，
再加一层手写索引是重复脚手架。（这正是 ponytail 的第一级台阶：它需要存在吗？）

## 三、产出清单（就是本目录）

```text
workflowproject-kit-v2/
├── README.md                    ← 本文件：总览 + 落地步骤 + 验收
├── PRUNE.md                     ← 该删/该合并的清单（4,225 行同构样板等）
├── patch-export_unified_kit.md  ← 生成器的 3 处精确改动（含行号与替换文本）
└── repo-payload/                ← 这些文件拷进 WorkflowProject 仓库
    ├── _unified-src/            ← 【新增】手维护源目录，生成器不再 rmtree 它
    │   ├── SKILL.md             ← 新入口（门禁表，≤120 行）★核心
    │   ├── AI-WORKFLOW-RULES.md ← 独立内容，不再与 AGENTS.md 重复
    │   ├── gates/01..08-*.md    ← 8 个门禁（按需单独读）
    │   ├── templates/*.md       ← 3 个模板（门禁的产出载体）
    │   └── scripts/check_gates.py ← 可运行门禁校验 ★核心
    └── developer-kit/
        └── workflows/developer/refactor-workflow.md ← 重构升为一等公民
```

**为什么放这些位置**（重要，别放错，否则你下次导出会静默覆盖）：

- `14-exports/workflowproject-kit/` 是**生成物**——`tools/export_unified_kit.py:640` 是
  `shutil.rmtree(OUTPUT)`，手写进去的东西下次导出就没。
- `14-exports/<子能力包>/` 是**手维护源目录**，生成器整目录 `copy_tree` 它们。
  → **往子能力包里加文件不需要改生成器**，所以 `refactor-workflow.md` 放这里。
- 新增的 `_unified-src/` 是我引入的第二个手维护源目录，需要生成器加**一行** copy_tree。
- 入口 `SKILL.md` 现在是脚本里的内联常量 `UNIFIED_SKILL`（L26–136），
  **必须改脚本**才能换掉（见 patch 文件第 1 处）。

## 四、落地步骤

### 批 1｜注册 5 个能力包（先做这个，0.2 会话，收益最大）

harness 只扫一层。把嵌套的能力包**符号链接**到被扫描的根：

```bash
S="$HOME/.codex/skills"
K="$HOME/Library/Application Support/dsh-desktop/harness/skills/workflowproject-kit/kits"
for k in developer-kit ui-designer-kit tester-kit team-orchestration-kit project-governance-kit; do
  [ -e "$S/$k" ] || ln -s "$K/$k" "$S/$k"
done
ls -la "$S"
```

**重启 DSH**，然后确认目录里出现 5 个新 skill（我也会在下一轮会话核对）。

> ⚠️ 要你拍板：**`product-manager-kit` 有两份不同内容**
> （`~/.codex/skills/product-manager-kit` 独立版 vs `workflowproject-kit/kits/product-manager-kit` 嵌套版）。
> 建议保留 `~/.codex` 那份（已在用）并删掉嵌套版，否则两份会漂移。
> 上面脚本因此**故意跳过了 product-manager-kit**。

### 批 2–4｜拷入 v2 内容并重新导出

```bash
R="$REPO"
V="<kit>/repo-payload"

# 1) 新增手维护源目录 + 重构工作流
cp -R "$V/_unified-src"                       "$R/14-exports/_unified-src"
cp    "$V/developer-kit/workflows/developer/refactor-workflow.md" \
        "$R/14-exports/developer-kit/workflows/developer/refactor-workflow.md"

# 2) 按 patch-export_unified_kit.md 改生成器（3 处）
#    改完重新导出：
cd "$R" && python3 tools/export_unified_kit.py

# 3) 覆盖安装到 skill 根（让改动生效）
S="$HOME/Library/Application Support/dsh-desktop/harness/skills/workflowproject-kit"
cp -R "$R/14-exports/workflowproject-kit/." "$S/"

# 4) 验证：对**目标项目**跑门禁校验（不是对 kit 跑）
python3 "$S/scripts/check_gates.py" /path/to/some/project
python3 "$S/scripts/check_gates.py" --audit /path/to/some/project   # 找出没证据的门禁（死规则）
```

### 批 5｜提交

```bash
cd "$R"
git add 14-exports tools/export_unified_kit.py
git commit -m "优化 workflowproject-kit：能力包注册修复、入口改门禁表、补 8 个门禁、生成器去重"
git push
```

**建议把「skill 安装」也纳入版本管理**：`~/.codex/skills/*` 目前是散落的拷贝，
没有版本控制。可考虑把安装动作脚本化（例如仓库里加 `tools/install_skills.sh`），
这样"skill 装了什么版本"可追溯。这一步我没有产出，因为需要你先决定安装形态（符号链接 vs 拷贝）。

## 七、验收：不靠自我感觉

### 已实测的产出指标

| 指标 | 现状 | 目标 | **实测结果** |
|---|---|---|---|
| 入口必读行数 | 27,488（须全读才合规） | ≤120 | ✅ **110 行** |
| frontmatter 可注册性 | — | name + 含路由触发词的 description | ✅ `name: workflowproject-kit` + 185 字符描述（含「已有/重构/审计/接手」4 个触发词） |
| 门禁文件 | 0 | 8 | ✅ 8 个 + 3 个模板 |
| 可运行守卫 | **0** | ≥1 | ✅ `check_gates.py`，**实测会报红**（见下） |
| 产出总篇幅 | 27,488 行 | 远小于 | ✅ **1,835 行（6.7%）** |
| 同构样板占比 | 15% | <3% | ⬜ 需执行 PRUNE 后才可测 |

### `check_gates.py` 的三次实测（不是"应该能跑"）

| 用例 | 结果 |
|---|---|
| **空项目** | 4 个硬门禁报红 + 每条给可操作提示 + **退出码 1** ✅ |
| **合格项目**（手写最小 AGENTS.md + 守卫文件） | 硬门禁全过 + **退出码 0** ✅ |
| **真实项目 StockTools** | **5/8 有证据，门禁 01（基线）报红** —— 抓到真问题 ✅ |

第三次测试**抓到了一个我自己的真实缺口**：`AGENTS.md` 里没有「基线」段，
而且写的「期望 188 passed」**已过期**（实际 196）。补齐后 8/8 通过、退出码 0、测试仍 196 passed。

**这就是整个方案要的效果**：规范不再是"文档里的一句话"，而是**一条会报红的命令**。

### 最后一条验收（需要你参与）

**规范命中率**：跑一个真实的中等任务（例如"给一个已有项目加一个新页面"），
记录**哪些门禁真的被触发、产出了什么**。

**没有被触发的门禁就是死规则 —— 应该删掉或改触发条件。** 这是对 kit 自身做 ponytail：
**规则不是越多越好，是被用到才算数。**
