# 角色能力包生命周期标准

## 目的

本标准用于统一所有角色能力包的总入口设计。

它解决的问题是：后续新增产品经理、开发、UI 设计、测试、运营等角色时，不要每个角色各写一套入口逻辑，导致使用方式、阶段推进、确认规则和结束标准不一致。

## 适用范围

适用于所有角色能力包：

```text
product-manager-kit/
developer-kit/
ui-designer-kit/
tester-kit/
operator-kit/
```

也适用于 WorkflowProject 内部角色总入口：

```text
04-workflows/{role}/{role}-workflow.md
04-workflows/{role}/{role}-kit-workflow.md
```

## 核心共性

产品经理角色和开发角色虽然产出不同，但在 AI 协作开发过程中有相同的治理骨架：

| 共性 | 产品经理角色表现 | 开发角色表现 |
| --- | --- | --- |
| 总入口不是分流器 | 不只是判断需求分析、PRD、验收标准 | 不只是判断项目理解、实现、测试 |
| 必须有生命周期 | 想法到需求、PRD、验收、版本、复盘 | 需求到项目理解、规划、实现、验证、评审、复盘 |
| 阶段结束要判断下一步 | 需求分析后判断是否进入 PRD | 影响分析后判断是否进入实现 |
| 关键阶段前要确认 | PRD、版本规划、开发交接前确认 | 实现、发布、高风险变更前确认 |
| 信息不足要主动询问 | 目标用户、场景、范围不清时询问 | 方案、风险、模块边界不清时询问 |
| 必须区分事实和推断 | 不把 AI 推断写成确定需求 | 不把 AI 推断写成确定架构或改动范围 |
| 必须有执行状态 | 当前阶段、工作流、下一步 | 当前阶段、工作流、下一步 |
| 必须有结束标准 | 文档完成后判断是否进入下一产品阶段 | 代码完成后判断验证、文档、评审、发布 |
| 执行型任务要可拆解 | 功能规划拆成范围、优先级和版本 | 实现拆成开发任务列表并逐条执行 |
| 必须有外部使用体验 | INSTALL、示例、工具说明 | INSTALL、示例、工具说明 |

## 统一角色能力包结构

所有导出角色能力包建议使用以下结构：

```text
{role}-kit/
├── START-HERE.md
├── README.md
├── usage-guide.md
├── INSTALL.md
├── SKILL.md
├── manifest.md
├── workflows/
│   └── {role}/
│       └── {role}-workflow.md 或 {role}-kit-workflow.md
├── templates/
│   └── {role}/
├── scorecards/
├── knowledge/
├── examples/
│   └── quick-start-example.md
└── integrations/
    ├── codex-usage.md
    └── cursor-usage.md
```

## 统一主入口职责

每个角色能力包必须有一个主入口工作流。

主入口工作流不是万能模板，也不是单点分流器。

它必须负责：

1. 判断当前任务属于哪个角色阶段。
2. 判断是否需要先补输入或澄清问题。
3. 选择当前阶段的细分工作流。
4. 说明为什么选择这个工作流。
5. 判断当前阶段完成后是否进入下一阶段。
6. 在关键阶段前请求用户确认。
7. 在信息不足或风险较高时主动询问用户。
8. 输出执行状态。
9. 按任务结束标准收尾。

## 总调度优先规则

当外部项目同时存在团队总调度能力包和具体角色能力包时，应默认先由团队总调度入口接管产品、UI、开发、测试相关任务。

团队总调度先判断：

- 当前任务是否跨角色。
- 哪些角色需要参与。
- 谁应该先接管。
- 当前阶段完成后是否需要下游角色接手。
- 是否存在交接阻塞或验收风险。

具体角色包直接接管的条件：

- 外部项目没有团队总调度能力包。
- 用户明确要求只使用某个具体角色包。
- 团队总调度已判断为纯单角色轻量任务，并说明不需要跨角色协作。

### Skill 与子 Agent 的分流

总调度先判断任务复杂度，不代表所有任务都要创建子 Agent：

- 简单单角色任务直接调用对应 Skill，执行模式为“单 Agent + Skill”。
- 组合任务才建立父 Agent 任务树并创建真实子 Agent。
- 没有真实子 Agent 工具时，必须先说明能力限制；未经用户确认不得将单 Agent 顺序执行描述为子 Agent 协作。

推荐路由：

```text
用户任务
-> team-orchestration-kit
-> product-manager-kit / ui-designer-kit / developer-kit / tester-kit
```

## 统一生命周期模型

所有角色总入口都应遵守下面的抽象生命周期：

```text
任务识别
-> 输入标准化
-> 当前阶段分析
-> 是否进入下一阶段确认
-> 整体规划
-> 任务拆解
-> 执行产出
-> 质量检查
-> 文档或结果同步
-> 后续流转判断
-> 复盘沉淀
```

不同角色可以把阶段映射成自己的专业语言。

### 产品经理映射

```text
任务识别
-> 想法标准化
-> 需求分析
-> 是否进入 PRD
-> PRD
-> 验收标准
-> 功能规划
-> 优先级和版本规划
-> 需求池或路线图
-> 变更评估或版本复盘
```

### 开发角色映射

```text
任务识别
-> 需求理解
-> 是否确认进入开发
-> 项目理解
-> 功能整体规划
-> 开发任务拆解
-> 风险和影响范围确认
-> 代码实现
-> 测试验证
-> 文档同步
-> 代码评审
-> 发布或复盘判断
```

## 统一执行状态格式

所有角色能力包在执行前或阶段切换时，都应输出：

```text
当前阶段：{角色内阶段}
任务判断：{任务类型}
调用能力包：{kit-name}
使用工作流：{workflow}
使用模板：{template}
检查标准：{scorecard}
执行方式：{只分析 / 先确认后继续 / 直接产出 / 先方案后实现}
是否需要用户确认：{是 / 否}
已完成：{已完成内容}
正在执行：{当前动作}
下一步：{下一阶段或等待确认}
保存位置：{对话直接输出 / 用户指定目录 / 已有文档目录 / docs/ / 直接修改项目}
```

如果某个字段不适用，可以写：

```text
不适用，原因：{原因}
```

## 统一主动询问规则

遇到以下情况，不要自作主张：

- 用户目标不清楚。
- 输入材料互相冲突。
- 当前阶段进入下一阶段的条件不足。
- 会影响范围、成本、风险、交付时间或团队协作方式。
- 存在多个合理方案，且没有明显最优解。
- 用户没有明确验收标准。
- AI 的判断依赖推断而不是事实。

推荐询问格式：

```text
我现在不能直接进入 {下一阶段}，因为 {原因}。
需要你确认：
1. {关键问题 1}
2. {关键问题 2}

如果你希望我先按默认假设推进，我会按 {默认假设} 处理，并把它标记为 AI 推断。
```

## 统一阶段门禁

每个角色都要定义自己的关键阶段门禁。

- 进入关键产出前，必须确认输入是否足够。
- 进入跨角色交接前，必须确认边界、风险和验收标准。
- 进入高成本或高风险动作前，必须请求用户确认。
- 如果门禁不满足，先补上游阶段，不要强行进入下一步。

| 角色 | 关键门禁 |
| --- | --- |
| 产品经理 | 进入 PRD 前必须完成需求分析质量检查 |
| 产品经理 | 进入开发交接前必须有验收标准和范围边界 |
| 开发 | 进入实现前必须有项目理解和功能整体规划 |
| 开发 | 进入实现前必须检查项目设计规范、开发规范、测试规范和 AI 协作规则 |
| 开发 | 进入实现前必须做最小必要变更判断，避免过度设计、过早抽象和不必要依赖 |
| 开发 | 中高风险实现前必须有开发任务列表 |
| 开发 | 进入发布前必须有测试验证和回滚判断 |
| UI 设计 | 进入页面结构或组件设计前必须明确页面目标、用户场景和信息优先级 |
| UI 设计 | 进入设计交接前必须说明关键状态、可用性风险和待确认问题 |
| 测试 | 进入测试用例设计前必须明确测试范围、验收标准和关键路径 |
| 测试 | 进入发布验收判断前必须说明回归范围、缺陷风险和未覆盖项 |

## 执行型任务拆解规则

如果某个角色进入“执行产出”阶段，并且任务会产生多个文件、多个模块或多个步骤的变化，应先拆成任务列表。

任务列表至少包含：

```text
序号
任务
目标
影响文件或模块
前置依赖
验收标准
验证方式
状态
```

执行规则：

```text
一次只执行一条任务
-> 完成本条任务的最小改动
-> 验证本条任务
-> 记录结果
-> 判断是否进入下一条任务
```

不应在未验证当前任务前，同时推进多条任务。

## 统一任务结束标准

任务结束前必须说明：

- 当前阶段是否完成。
- 是否已经进入或不进入下一阶段。
- 如果停止，停止原因是什么。
- 是否存在待确认问题。
- 输出是否经过对应 scorecard 或质量检查。
- 输出是否保存，保存位置是什么。
- 是否需要同步文档、交接、评审、发布或复盘。
- 下一步建议是什么。

如果该角色任务属于长期迭代项目，还必须判断是否需要更新项目记忆摘要：

```text
00-progress/memory-summary.md
```

当本轮产生新的关键决策、当前状态、风险、下一步或可用资产时，应更新摘要，避免后续 AI 每次读取完整历史。

如果这些信息没有说明完整，不应直接宣称任务完成。

## 统一外部使用体验

每个导出能力包必须包含：

| 文件 | 作用 |
| --- | --- |
| `START-HERE.md` | 外部 AI 和用户的统一入口 |
| `README.md` | 能力包说明 |
| `usage-guide.md` | 使用步骤和工作流选择 |
| `INSTALL.md` | 首次接入说明 |
| `examples/quick-start-example.md` | 快速启动示例 |
| `integrations/codex-usage.md` | Codex 使用说明 |
| `integrations/cursor-usage.md` | Cursor 使用说明 |
| `SKILL.md` | Codex skill 草稿 |
| `manifest.md` | 来源和维护说明 |

## 统一输出目录策略

当能力包在外部项目中使用，并且用户要求保存结果时，统一按以下顺序处理：

1. 用户明确指定输出目录时，使用用户指定目录。
2. 项目已有统一文档目录时，使用已有目录，例如 `docs/`、`documents/`。
3. 项目已有角色文档目录时，使用该目录，例如 `docs/product/`、`docs/dev/`。
4. 如果没有合适目录，再在项目根目录创建 `docs/`。

不要在外部项目中默认创建或使用 WorkflowProject 内部目录，例如：

```text
{目标文档目录}/
12-projects/
```

## 统一质量检查

每个角色能力包至少检查：

- 是否有主入口工作流。
- 主入口是否是生命周期编排器，而不是单点分流器。
- 是否有执行状态格式。
- 是否有任务结束标准。
- 是否有主动询问规则。
- 是否有关键阶段门禁。
- 是否有首次接入说明。
- 是否有快速启动示例。
- 是否有 Codex 和 Cursor 使用说明。
- 是否有 scorecard 或质量检查方式。
- 是否避免把 WorkflowProject 内部目录带到外部项目。
- 是否在导出或更新后刷新 `12-projects/asset-index.md`，让使用者能从全局入口找到该能力包。

## 后续新增角色的标准建设顺序

新增角色能力包时，建议按以下顺序建设：

1. 定义角色边界。
2. 定义角色生命周期。
3. 建立角色总入口工作流。
4. 拆分细分工作流。
5. 建立模板。
6. 建立评分表。
7. 跑真实案例验证。
8. 沉淀知识和示例。
9. 导出能力包。
10. 补齐使用体验层。
11. 刷新项目索引、资产索引、控制台数据和 XMind。
12. 检查是否符合本标准。

刷新命令：

```bash
python3 tools/refresh_maps.py
```
