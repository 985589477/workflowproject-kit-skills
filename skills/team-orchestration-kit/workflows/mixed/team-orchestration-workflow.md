# 跨角色团队总调度工作流

## 目的

用于把产品经理、UI 设计师、开发工程师、测试工程师组织成一个完整 AI 协作团队。

当用户提出产品需求、功能想法、设计任务、开发任务、缺陷、优化、上线或复盘问题时，本工作流先判断哪些角色需要参与，再按优先级引导用户从需求到设计、开发、测试、验收和复盘逐步推进。

本工作流不是替代任何单一角色，而是负责跨角色调度、交接检查、互相验收和沟通问题反馈。

## 什么时候使用

```text
请使用跨角色团队总调度处理我的需求：{写下你的需求}
```

## 总调度优先规则

当外部项目中存在跨角色团队总调度入口时，产品、UI、开发、测试相关任务默认先由总调度接管。

总调度先判断：

- 这是单角色任务，还是跨角色任务。
- 是否需要多个角色连续协作。
- 当前应该由哪个角色先接管。
- 当前角色完成后是否需要交接给下一个角色。
- 是否需要下游角色验收上游产物。

只有在以下情况，才由具体角色直接接管：

- 外部项目没有总调度入口。
- 用户明确指定只使用某个角色包。
- 总调度判断这是纯单角色轻量任务，并说明不需要跨角色协作。

因此默认路由是：

```text
用户提出任务
-> team-orchestration-kit 先接管判断
-> 如需跨角色，按产品/UI/开发/测试链路推进
-> 如为单角色任务，转交对应角色包
```

适合以下场景：

- 用户提出一个完整功能需求，不确定应该先找产品、UI、开发还是测试。
- 一个任务需要产品、UI、开发、测试连续协作。
- 需要检查上游产物是否能被下游角色理解。
- 需要判断开发交付是否能通过产品、UI、测试验收。
- 角色之间出现沟通不畅，需要记录 badcase 并回到对应角色项目优化。

## 团队角色

| 角色 | 主要职责 | 典型输入 | 典型输出 |
| --- | --- | --- | --- |
| 产品经理 | 明确问题、目标用户、需求范围、PRD、验收标准、优先级 | 想法、业务目标、用户反馈 | 需求分析、PRD、验收标准、版本范围 |
| UI 设计师 | 明确设计规范、信息架构、页面结构、组件、适配和设计交接 | PRD、页面目标、品牌规范 | UI brief、设计规范、页面结构、组件规划、开发实现约束 |
| 开发工程师 | 理解项目、划分模块、规划实现、编码、验证、文档同步 | PRD、设计交接、验收标准 | 技术方案、任务拆解、代码实现、测试验证、交付说明 |
| 测试工程师 | 检查验收标准、测试策略、用例、回归、缺陷、发布验收 | PRD、开发变更、设计交接 | 测试策略、测试用例、缺陷报告、测试报告、发布建议 |

## 总生命周期

```text
用户输入
-> 需求识别和角色判断
-> 产品经理接管：需求分析/PRD/验收标准
-> UI 设计师接管：设计规范/页面结构/组件/适配/设计交接
-> 开发工程师接管：项目理解/方案规划/任务拆解/实现/验证
-> 测试工程师接管：验收标准检查/测试策略/用例/回归/发布验收
-> 跨角色互审
-> 交付结论
-> badcase 反馈和能力优化建议
```

不是每个需求都必须经过所有角色。跳过角色时必须说明原因。

## 角色接管判断

| 用户输入特征 | 优先接管角色 | 后续协作角色 |
| --- | --- | --- |
| 只有想法、业务目标、用户问题 | 产品经理 | UI、开发、测试 |
| 已有 PRD，需要页面方案 | UI 设计师 | 产品、开发、测试 |
| 已有明确需求和设计，需要实现 | 开发工程师 | 产品、UI、测试 |
| 已有开发变更，需要验证 | 测试工程师 | 产品、开发、UI |
| 用户反馈 bug | 测试工程师 | 开发、产品、UI |
| 上线前检查 | 测试工程师 | 产品、开发、UI |
| 需求跨越多个角色且不明确 | 总调度先接管 | 按阶段逐步调度 |

## 角色优先级

默认优先级：

```text
产品经理 -> UI 设计师 -> 开发工程师 -> 测试工程师
```

例外：

- 如果用户输入是 bug，测试工程师优先接管。
- 如果用户输入是代码实现或报错，开发工程师优先接管。
- 如果用户输入是视觉、交互、页面、组件、适配，UI 设计师优先接管。
- 如果用户输入是上线、回归、验收、缺陷复现，测试工程师优先接管。

## 跨角色交接门禁

### 产品到 UI

UI 设计师接收产品输出前，必须检查：

- 页面目标是否清楚。
- 用户场景是否清楚。
- 需求范围和非范围是否清楚。
- 验收标准是否足够支撑设计判断。
- 是否存在影响页面结构的业务规则。

如果看不懂，反馈给用户：

```text
产品到 UI 交接不通过：{原因}
需要补充：{问题列表}
建议回到产品经理能力包优化：{具体 workflow}
```

### 产品到开发

开发工程师接收产品输出前，必须检查：

- PRD 是否明确功能范围。
- 验收标准是否可测试。
- 业务规则、权限、数据状态是否清楚。
- 是否存在技术方案无法判断的缺口。

### UI 到开发

开发工程师接收 UI 输出前，必须检查：

- 设计规范是否清楚。
- 页面结构、组件、状态、适配是否清楚。
- 是否有开发实现约束。
- 特殊设备、响应式、异常状态是否说明。

### 产品/UI/开发 到测试

测试工程师接收上游输出前，必须检查：

- 验收标准是否可测试。
- 测试范围和非范围是否清楚。
- 开发变更范围是否清楚。
- 设计状态、异常、兼容和非功能风险是否清楚。

### 开发交付到三方验收

开发交付后必须让三方分别验收：

| 验收方 | 验收重点 |
| --- | --- |
| 产品经理 | 是否满足需求目标、范围、验收标准 |
| UI 设计师 | 是否符合设计规范、页面结构、组件状态和适配 |
| 测试工程师 | 是否通过测试策略、用例、回归和发布验收 |

## 执行状态格式

```text
当前阶段：{团队协作阶段}
总调度判断：{当前任务类型}
参与角色：{产品经理 / UI 设计师 / 开发工程师 / 测试工程师}
当前接管角色：{角色}
调用能力包：{product-manager-kit / ui-designer-kit / developer-kit / tester-kit}
使用工作流：{workflow}
使用模板：{template}
检查标准：{scorecard}
是否需要用户确认：{是 / 否}
已完成：{已完成内容}
正在执行：{当前动作}

```

## 沟通不畅反馈规则

如果任何角色无法理解上游输出，或发现下游无法验收，必须停止推进并反馈：

```text
协作阻塞：{阻塞点}
发现角色：{角色}
来源角色：{角色}
问题类型：{需求不清 / 设计不清 / 技术边界不清 / 验收标准不清 / 测试不可执行 / 其他}
影响：{会影响什么}
建议补充：{问题列表}
建议回到：{角色能力包 + 工作流}
badcase 记录建议：{建议保存到哪个项目或 lessons}
```

## badcase 沉淀规则

当出现以下情况时，应建议用户把案例回流到 WorkflowProject：

- 某角色输出多次被下游看不懂。
- 交接文档缺少固定字段。
- 同类问题反复出现。
- 总调度无法判断接管角色。
- 角色之间验收标准冲突。

badcase 应记录：

- 原始用户输入。
- 当时调用的角色和工作流。
- 哪个角色发现问题。
- 哪个字段或交接内容导致问题。
- 期望改进的角色能力。
- 建议回到哪个 capability-building 项目优化。

## 主动询问规则

遇到以下情况必须先询问用户：

- 是否进入开发实现。
- 是否需要多角色完整链路，还是只要某个角色阶段产出。
- 是否保存到外部项目文档目录。
- 需求范围、设计规范、开发边界或验收标准不清。
- 多个角色对下一步判断不一致。

## 结束标准

任务结束前必须说明：

- 本次有哪些角色参与。
- 每个角色完成了什么。
- 哪些交接通过，哪些不通过。
- 是否可以进入下一阶段。
- 是否存在 badcase 或能力优化建议。
- 下一步应该由哪个角色接管。
