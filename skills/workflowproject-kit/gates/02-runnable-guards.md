# 门禁 02：可运行守卫

**触发**：每当定下一条治理规则、架构约束、接口契约或"不许这么做"的要求时。

**为什么**：规则写在文档里**没人执行**；写成断言**每次跑测试都在执行**。
原 kit 全仓 grep `守卫|门禁测试` = **0 命中**——所有规范都停留在提示词层面，这是
M3「无强制」的直接原因。

在 StockTools 里，真正防住退化的东西**全是可运行守卫**，没有一条是文档：

| 守卫 | 防住什么 |
|---|---|
| 架构守卫测试（**双向精确清单**） | 分层违规。加一条违规 → 红；修好一条但没更新清单 → **也红**（这个"双向"是关键，单向清单会慢慢过期） |
| 路由契约快照（72 条路由 + 鉴权清单） | 悄悄新增未鉴权接口。快照 diff 就是审计日志 |
| golden 文件（选股回测成交序列） | 算法行为漂移 |
| token 完整性测试 | `var(--typo)` 静默失效（写错的引用**不报错**，只让声明失效） |

---

## 必须产出

**一条可运行的检查**，满足：

1. **能失败**：注入一个故意违规，确认它变红。**没变红 = 这条守卫是假的。**
2. **断言语义，不是实现**：断"不允许 X"，不要断"第 812 行是 Y"。
3. **失败信息可操作**：说清**哪个文件哪一行、该怎么做**，而不是 `assert False`。
4. **进入现有测试命令**：跑 `pytest` / `npm test` 就能覆盖，不要求人记得单独跑。

## 检查方式

```bash
# 1. 跑一次，必须绿
{测试命令}

# 2. 注入违规，必须红（把结果贴进产出）
{故意违规的操作}
{测试命令}   # 期望非 0 退出码

# 3. 撤销违规，重新变绿
```

**第 2 步不能省。** 我在 StockTools 里对每条守卫都做了这一步，其中架构守卫和鉴权清单
都因此发现了「守卫看起来在防、实际匹配不到」的问题。

## 双向精确清单（强烈推荐的一种守卫形态）

单向清单（"允许这些例外"）会**慢慢过期**：现实违规被悄悄加进清单，没人再管。
双向清单同时断言：

- 违规集合 **⊆** 已知清单（新增违规 → 红）
- 已知清单 **⊆** 违规集合（修好一条却没从清单删 → **也红**）

这样清单不可能腐烂。代价是**每次修复都必须同步改清单**——这正是你要的摩擦。

## 反例

| 反例 | 后果 |
|---|---|
| 只写进 `docs/` 的规则 | 无人执行，逐渐与代码背离 |
| 守卫正则太宽（`import.*repository`） | 匹配不到真实违规，看起来在防其实是摆设 |
| 守卫正则太窄，只匹配一种写法 | 换个写法就绕过（`import` vs 动态 import vs 字符串） |
| 把"已知违规清单"当免死金牌 | 清单只增不减，最后等于没有规则 |
| 守卫依赖真实数据/网络 | 换机器必红，然后被整体跳过 |

## 有意留下的捷径要登记

守卫做不到全覆盖时（比如静态扫描抓不到动态拼 SQL），**在代码里写清楚**：

```python
# ponytail: 用正则扫源码行，抓不到「动态拼 SQL 再 execute」这类绕法;
#           升级路径：改成 AST 分析或引入 sqlalchemy 事件钩子
```

并在收尾时登记进台账，**不要让它烂成"以后再说就是永远不做"**。
