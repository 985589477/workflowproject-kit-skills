# 需求池管理工作流

## 目的

把来自用户反馈、业务输入、需求分析、竞品分析、产品策略判断和团队讨论的需求整理成可长期维护的需求池，帮助产品经理追踪需求来源、当前状态、价值线索、优先级、版本归属和后续动作。

本工作流重点解决：

1. 避免需求分散在不同文档里无法追踪。
2. 保留需求来源和判断依据。
3. 让需求从进入、澄清、分析、判断、PRD、版本规划到归档有清楚状态。
4. 区分可推进、待澄清、暂缓、拒绝和已归档需求。
5. 为需求分析、产品策略判断、优先级判断、PRD 和版本规划提供入口。

## 适用场景

适用于产品经理相关需求管理任务，包括：

- 整理多个来源的需求。
- 把用户反馈转入需求池。
- 把业务方想法转入需求池。
- 管理需求状态和下一步动作。
- 从需求池中筛选要进入分析、PRD 或版本规划的需求。
- 周期性复盘需求池。

## 输入要求

至少需要以下一种输入：

- 用户反馈整理结果。
- 需求分析结果。
- 产品策略判断结果。
- 竞品分析结果。
- 业务方需求列表。
- 会议纪要。
- 历史需求池。

建议同时说明产品目标、当前版本目标、资源约束、已有优先级判断、版本规划和不再推进的边界。

## 执行步骤

### 第 1 步：确认管理目标

- 明确本次是新建需求池、更新需求池，还是复盘需求池。
- 明确本次需求池服务于哪个产品、版本或阶段。
- 明确不进入本次需求池的范围。

产出：`{目标文档目录}/requirement-pool-goal.md`

### 第 2 步：汇总需求来源

- 汇总用户反馈、业务输入、竞品启发、策略判断和需求分析结果。
- 保留每条需求的来源。
- 合并重复或高度相似的需求。

产出：`{目标文档目录}/requirement-sources.md`

### 第 3 步：分类和标准化需求

- 为需求命名。
- 标记需求类型，例如问题修复、体验优化、新功能、增长、商业化、合规、技术债。
- 标记目标用户、场景和价值线索。
- 标记信息不足项。

产出：`{目标文档目录}/requirement-normalization.md`

### 第 4 步：标记需求状态

- 根据当前信息为每条需求标记状态。
- 不确定需求进入待澄清。
- 明显不符合目标的需求进入拒绝或归档。
- 有推进可能但当前不做的需求进入暂缓。

产出：`{目标文档目录}/requirement-status.md`

### 第 5 步：确定下一步动作

- 判断每条需求应该进入需求分析、策略判断、优先级判断、PRD、版本规划，还是继续补充信息。
- 标记风险、依赖和待确认问题。
- 给出维护建议。

产出：`{目标文档目录}/requirement-pool.md`

### 第 6 步：评审需求池

- 检查需求来源是否可追溯。
- 检查状态是否清楚。
- 检查是否保留下一步动作。
- 检查是否避免把所有需求默认推进。
- 检查是否可以支持后续产品工作流。

产出：`05-review/requirement-pool-review.md`

## 推荐状态

| 状态 | 含义 | 常见下一步 |
| --- | --- | --- |
| 新进入 | 刚进入需求池，尚未整理 | 分类和标准化 |
| 待澄清 | 信息不足，需要补充背景 | 补充输入或访谈 |
| 待分析 | 可以进入需求分析 | 需求分析 |
| 待判断 | 需要策略或优先级判断 | 策略判断或优先级判断 |
| 待 PRD | 已确认推进，需要产品文档 | PRD 生成 |
| 待版本规划 | 已有范围，需要安排阶段 | 版本规划 |
| 暂缓 | 方向可能成立，但当前不做 | 定期复盘 |
| 拒绝 | 不符合目标或价值不足 | 记录原因 |
| 已归档 | 已完成、失效或不再跟进 | 保留记录 |

## 质量标准

- 需求来源可追溯。
- 需求分类清楚。
- 每条需求都有当前状态。
- 信息不足需求没有被强行推进。
- 暂缓、拒绝和归档有理由。
- 每条重要需求都有下一步动作。
- 能衔接需求分析、策略判断、优先级判断、PRD 或版本规划。
