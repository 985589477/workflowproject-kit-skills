# 需求分析工作流

## 目的

把用户想法、业务背景、需求草稿、用户反馈或会议纪要整理成结构化需求分析结果。

本工作流重点解决：

1. 明确真正要解决的问题。
2. 明确目标用户和使用场景。
3. 区分事实、AI 推断和待确认信息。
4. 明确需求边界和不做范围。
5. 为 PRD、功能规划和验收标准提供可靠上游输入。

## 适用场景

适用于产品经理相关需求分析任务，包括：

- 用户只有一句产品想法。
- 用户提供了模糊需求。
- 用户已有需求草稿，但结构混乱。
- 用户提供了会议纪要，希望整理为需求。
- 用户提供了用户反馈，希望提炼需求机会。
- 后续需要生成 PRD、功能规划或验收标准。

如果用户完全没有输入，应先使用：

```text
06-templates/meta/idea-to-input-generator.md
04-workflows/common/idea-to-input-workflow.md
```

生成标准输入。

## 输入要求

建议输入材料放在：

```text
{目标文档目录}/
```

至少准备以下一种输入：

- 用户原始想法。
- 需求草稿。
- 业务背景。
- 用户反馈。
- 会议纪要。
- 竞品参考。
- 数据现象。
- 页面或功能说明。

如果信息完整，建议包含：

1. 背景：为什么提出这个需求。
2. 目标：希望解决什么问题。
3. 用户：面向谁。
4. 场景：用户在什么情况下使用。
5. 现状：现在怎么做，有什么问题。
6. 约束：业务、技术、时间、资源或合规限制。
7. 期望输出：希望后续生成 PRD、功能清单、验收标准还是其他内容。

## 执行步骤

### 第 1 步：确认输入是否足够

输入：

- `01-inputs/original-requirement.md`
- 其他原始材料。

处理动作：

- 判断是否已有标准输入。
- 如果只有一句想法，先转成标准输入。
- 如果已有材料但结构混乱，先整理材料结构。
- 标记缺失信息。

产出：

```text
{目标文档目录}/input-readiness.md
```

### 第 2 步：提取需求背景

输入：

- 标准输入。
- 原始材料。

处理动作：

- 提取业务背景。
- 提取触发原因。
- 提取相关角色。
- 标记资料来源。

产出：

```text
{目标文档目录}/requirement-background.md
```

### 第 3 步：识别核心问题

输入：

- 需求背景。
- 用户描述。
- 用户反馈或现状材料。

处理动作：

- 判断用户真正想解决的问题。
- 区分表层诉求和底层问题。
- 标记问题是否已被材料证明。
- 对不确定问题写入待确认。

产出：

```text
{目标文档目录}/problem-definition.md
```

### 第 4 步：明确目标用户和场景

输入：

- 核心问题。
- 原始材料。

处理动作：

- 提取目标用户。
- 提取使用场景。
- 标记关键用户动作。
- 判断是否有多类用户或多类场景。

产出：

```text
{目标文档目录}/user-scenarios.md
```

### 第 5 步：定义目标和成功标准

输入：

- 核心问题。
- 用户场景。
- 业务背景。

处理动作：

- 明确本需求要达成什么目标。
- 明确用户成功标准。
- 明确业务成功标准。
- 标记无法衡量或需要补充的数据。

产出：

```text
{目标文档目录}/product-goals.md
```

### 第 6 步：划定需求边界

输入：

- 目标。
- 场景。
- 约束条件。

处理动作：

- 明确本次要做什么。
- 明确本次不做什么。
- 标记可选范围。
- 标记后续版本可能处理的内容。

产出：

```text
{目标文档目录}/requirement-scope.md
```

### 第 7 步：整理事实、推断和待确认

输入：

- 所有分析结果。

处理动作：

- 将用户明确提供的信息列为事实。
- 将 AI 根据上下文判断的内容列为推断。
- 将影响后续输出但未确认的信息列为待确认。
- 不把推断写成事实。

产出：

```text
{目标文档目录}/facts-assumptions-questions.md
```

### 第 8 步：输出需求分析结论

输入：

- 背景。
- 问题。
- 用户和场景。
- 目标。
- 边界。
- 事实、推断和待确认。

处理动作：

- 汇总成一份可供后续使用的需求分析文档。
- 明确是否可以进入 PRD。
- 如果不能进入 PRD，说明缺什么。

产出：

```text
{目标文档目录}/requirement-analysis.md
```

## 输出结果

一次完整需求分析项目建议包含：

```text
{目标文档目录}/input-readiness.md
{目标文档目录}/requirement-background.md
{目标文档目录}/problem-definition.md
{目标文档目录}/user-scenarios.md
{目标文档目录}/product-goals.md
{目标文档目录}/requirement-scope.md
{目标文档目录}/facts-assumptions-questions.md
{目标文档目录}/requirement-analysis.md
```

如果项目较小，也可以合并为：

```text
{目标文档目录}/requirement-analysis.md
```

推荐最终需求分析文档包含：

```md
# 需求分析

## 背景

## 核心问题

## 目标用户

## 使用场景

## 产品目标

## 范围边界

## 已知事实

## AI 推断

## 待确认问题

## 是否可以进入 PRD
```

## 质量检查

执行完成后检查：

- 是否保留用户原始描述。
- 是否明确资料来源。
- 是否说明核心问题。
- 是否区分表层诉求和底层问题。
- 是否明确目标用户和使用场景。
- 是否明确产品目标。
- 是否明确做什么和不做什么。
- 是否区分事实、AI 推断和待确认信息。
- 是否说明是否可以进入 PRD。
- 是否能作为 PRD、功能规划和验收标准的上游输入。

## 常见分支

### 分支 A：只有一句想法

先使用 `idea-to-input-generator` 生成标准输入，再进入需求分析。

### 分支 B：材料很多但混乱

先整理材料来源和主题，再提取问题、用户、场景和边界。

### 分支 C：需求其实是解决方案

如果用户直接提出“我要做某功能”，需要反推底层问题，避免直接把方案当需求。

### 分支 D：缺少用户或场景

可以输出初版需求分析，但必须将用户和场景标记为待确认。

### 分支 E：可以进入 PRD

需求分析完成后，进入：

```text
04-workflows/product-manager/prd-workflow.md
```

如果 PRD 工作流尚未建设，先使用产品经理总入口工作流继续推进。

## 使用注意事项

- 需求分析不是 PRD，不需要完整功能规则。
- 不要在输入不足时编造用户、数据或业务背景。
- 如果需求本身不清楚，优先输出澄清问题。
- 需求分析的价值在于帮助后续产物更准确，而不是一次性完成所有产品文档。
- 后续如果本工作流被频繁使用，应继续沉淀需求分析模板和评分表。
