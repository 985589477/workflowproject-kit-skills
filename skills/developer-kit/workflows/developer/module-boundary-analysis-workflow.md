# 模块边界分析工作流

## 目的

当需求涉及多个模块、模块职责不清或可能新增模块时，帮助 AI 判断模块边界和协作方式。

本工作流重点解决：

1. 一个能力应该放在哪个模块。
2. 现有模块是否职责过载。
3. 是否需要新增模块。
4. 模块负责什么、不负责什么。
5. 模块之间应该如何调用、传参和返回。
6. 哪些依赖方向不应该出现。

一句话：

```text
模块边界分析 = 让 AI 知道代码应该放在哪里，以及不应该放在哪里。
```

## 适用场景

适用于：

- 需求影响多个模块。
- 不确定新能力应该放在哪个目录或模块。
- 一个模块已经变得很臃肿。
- 需要判断是否新增模块。
- 模块之间出现循环依赖、职责混杂或重复实现。
- 准备重构模块边界。

不适用于：

- 单文件小改动。
- 简单文案或样式修改。
- 项目还没有完成项目理解，应先使用 `project-understanding-workflow.md`。
- 需求影响范围还没分析，应先使用 `requirement-to-architecture-workflow.md`。

## 输入要求

至少需要：

- 需求或变更目标。
- 当前项目理解报告，或已有模块地图。

建议同时提供：

- 架构影响分析报告。
- 当前目录结构。
- 相关模块代码路径。
- 现有接口、数据结构或状态说明。
- 已知模块问题，例如职责混杂、重复代码、循环依赖。

## 执行原则

### 1. 职责单一

一个模块应围绕稳定业务概念或技术职责组织，不能把不相关能力塞到一起。

### 2. 边界显式

必须同时说明：

```text
负责什么
不负责什么
对外提供什么能力
依赖谁
被谁依赖
```

### 3. 先扩展已有模块，再新增模块

新增模块必须有明确理由，不能只是为了让文件看起来更整齐。

### 4. 依赖方向清晰

模块调用方向应尽量单向。基础模块不能反向依赖业务模块，通用工具不能混入具体业务。

### 5. 数据和状态归属明确

每类数据和状态都应有明确归属模块，避免多个模块同时修改同一状态。

## 执行步骤

### 第 1 步：确认分析对象

明确本次要分析的是：

- 单个模块。
- 多个相关模块。
- 一个新功能的模块归属。
- 一次重构边界。
- 一条完整业务链路。

产出：分析对象说明。

### 第 2 步：梳理现有模块

对相关模块建立当前画像：

```text
模块路径
当前职责
主要文件
对外能力
依赖模块
被调用方
关键数据或状态
当前问题
```

产出：现有模块画像。

### 第 3 步：判断职责归属

对需求中的每个能力点判断：

```text
属于已有模块
需要扩展已有模块
需要调整模块边界
需要新增模块
不应该由当前模块承担
```

产出：职责归属表。

### 第 4 步：判断是否新增模块

新增模块应满足多个条件：

- 出现新的稳定业务概念。
- 有独立生命周期。
- 未来可能被复用。
- 有明确输入输出。
- 有独立数据或状态。
- 可以独立测试。
- 放入已有模块会导致职责过载。

不建议新增模块的情况：

- 只是临时逻辑。
- 只是一个工具函数。
- 只是页面内部小逻辑。
- 没有独立业务含义。
- 只是为了拆文件。

产出：新增模块判断。

### 第 5 步：定义目标模块边界

对每个目标模块说明：

```text
模块职责
不负责范围
对外能力
输入
输出
依赖模块
禁止依赖
状态归属
数据归属
测试边界
```

产出：目标模块边界说明。

### 第 6 步：设计模块协作方式

说明模块之间如何协作：

- 谁调用谁。
- 传入什么。
- 返回什么。
- 异常由谁处理。
- 状态由谁拥有。
- 数据由谁持久化。
- 哪些调用方向禁止。

产出：模块协作设计。

### 第 7 步：识别边界风险

重点识别：

- 职责混杂。
- 循环依赖。
- 重复实现。
- 状态多处修改。
- 数据归属不清。
- 通用模块污染业务逻辑。
- 业务模块反向依赖页面。
- 新模块过度设计。

产出：边界风险清单。

### 第 8 步：输出模块边界分析报告

报告必须包含：

```text
分析对象
现有模块画像
职责归属判断
新增模块判断
目标模块边界
模块协作方式
边界风险
建议调整方案
后续工作流建议
```

## 快速启动话术

```text
请参考 04-workflows/developer/module-boundary-analysis-workflow.md，
基于当前项目和下面的需求，帮我做模块边界分析。

需求：
【粘贴需求】

请不要直接改代码，先输出模块画像、职责归属、新增模块判断、目标边界、模块协作方式、边界风险和下一步建议。
```

## 质量要求

- 必须说明模块负责什么和不负责什么。
- 必须说明依赖方向和禁止依赖。
- 新增模块必须有判断依据。
- 不能为了拆文件而新增模块。
- 必须识别状态和数据归属。
- 必须能支撑后续风险评估和实现工作流。
