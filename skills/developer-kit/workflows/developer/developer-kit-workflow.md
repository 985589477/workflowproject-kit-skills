# 开发治理总入口工作流

## 目的

这是开发角色的总入口。

当用户不确定该使用哪个开发工作流，或只给出一个产品需求、开发任务、项目问题、代码变更目标时，先使用本工作流进行判断和调度。

本工作流不是“命中一个细分工作流就结束”的路由器，而是开发治理主流程。

本工作流不负责替代所有细分工作流，而是负责：

1. 判断当前任务属于哪类开发治理问题。
2. 选择正确的开发细分工作流。
3. 判断是否需要先理解项目、分析风险或确认边界。
4. 说明为什么调度这个工作流。
5. 编排从需求到交付的完整开发链路。
6. 在实现前形成整体功能规划。
7. 在信息不足、风险较高或方向不明确时主动询问用户。
8. 明确执行方式、输出位置、验证方式和后续流转。

## 什么时候使用

当你不知道该选哪个开发工作流时，使用它。

典型说法：

```text
请使用开发治理总入口处理我的开发任务：{你的任务}
```

也可以直接说：

```text
我的开发任务是 {你的任务}，请帮我判断应该用哪个开发工作流，并继续执行。
```

## 总体原则

### 先理解，再改动

不要在不了解项目结构、模块边界、运行方式和用户已有改动的情况下直接改代码。

### 先判断风险，再选择深度

低风险任务可以轻量执行。

中风险任务需要先说明影响范围和实现计划。

高风险任务需要先输出风险、确认点和回滚策略。

### 先进入最小正确工作流

如果任务只是理解项目，不要进入实现。

如果任务只是判断影响范围，不要直接改代码。

如果任务涉及上线，不要跳过发布和回滚检查。

### 不以单点工作流作为终点

命中某个细分工作流只是当前阶段的开始，不代表任务结束。

每完成一个阶段后，都必须判断：

- 当前阶段是否已经完成。
- 是否需要用户确认。
- 是否可以进入下一阶段。
- 下一阶段应该使用哪个工作流。
- 是否需要回到上一阶段补充信息。

### 实现前必须先做整体规划

只要任务进入代码实现阶段，必须先形成整体功能规划。

整体功能规划至少说明：

- 要实现的用户目标。
- 本次包含和不包含的范围。
- 影响的模块、文件、接口、数据和配置。
- 功能拆分和实现顺序。
- 每个模块之间如何协作。
- 风险点和验证方式。
- 哪些地方需要用户确认。

没有整体规划，不进入代码实现。

### 实现前必须检查项目规范

进入功能整体规划或代码实现前，必须确认当前项目是否存在可遵守的设计规范、开发规范和协作规则。

需要检查的规范包括：

- UI 设计规范。
- 组件规范。
- 交互规范。
- 视觉规范。
- 代码风格。
- 架构约束。
- 目录约定。
- 命名规范。
- 测试规范。
- AI 协作规则，例如 `AGENTS.md`、`.cursor/rules/`、`AI-WORKFLOW-RULES.md`。
- 格式化和 lint 配置，例如 `.prettierrc`、`.eslintrc`、`biome.json`、`ruff.toml`。

如果规范存在，必须读取并遵守。

如果规范缺失，必须说明缺失项，并判断：

- 是否可以按现有代码模式轻量推断。
- 是否需要先补充规范。
- 是否需要用户确认后再实现。

如果涉及 UI、交互、组件或视觉变化，但没有对应设计规范，不要直接自作主张，应先询问用户或标记默认假设。

### 实现前必须确认技术方案

技术方案是进入新项目搭建或新模块实现前的独立问询门禁。

#### 新项目

如果当前没有可继承的项目技术栈，必须先询问：

```text
1. 目标平台是什么：网页、移动端、桌面端、服务端，还是其他？
2. 主要使用什么语言？
3. 是否指定框架及版本？如果没有，我可以提供 2-3 个方案供你选择。
4. 运行、构建和部署环境是什么？
5. 测试希望使用什么工具或方式？
```

在用户选择前，不创建工程骨架、不安装依赖、不生成新模块代码。

#### 已有项目的新模块

先从项目配置和源码中识别当前技术栈，并向用户确认：

```text
当前项目技术栈为：{语言 / 框架 / 运行时 / 构建方式}。
新模块是否沿用当前技术栈？是否允许引入新的语言、框架或独立运行时？
```

如果用户确认沿用，继续使用现有项目规范；如果用户希望引入新技术，必须补充技术选型理由、依赖影响、构建方式、测试方式和维护成本，再等待确认。

#### 只允许推断的情况

只有当项目规则已经明确写出技术栈，或现有项目配置和源码一致且用户已授权沿用时，才可以不重复询问。即使如此，也要在开发计划中展示识别到的技术方案。

### 实现前必须拆成开发任务列表

只要任务不是极小改动，进入代码实现前必须把整体规划拆成可逐条执行的开发任务列表。

开发任务列表至少说明：

- 每条任务的目标。
- 影响文件或模块。
- 前置依赖。
- 验收标准。
- 验证方式。
- 当前状态。

没有任务列表，不进入中高风险代码实现。

低风险小改动可以使用轻量任务列表，但仍要说明本次只做哪一条、如何验证、是否还有后续任务。

执行时必须遵守：

```text
一次只执行一条任务
-> 完成该任务的最小修改
-> 立即验证该任务
-> 记录结果
-> 判断是否进入下一条任务
```

不要一次性跨多条任务大范围修改。

### 实现前必须做最小必要变更判断

进入代码实现前，必须先判断本次变更是否存在过度设计风险。

必须输出：

```text
最小必要变更判断：
- 是否真的需要做：
- 是否可复用项目已有能力：
- 是否可用平台或标准库：
- 是否可用已安装依赖：
- 是否需要新增依赖：
- 最小完整方案：
- 明确不做的内容：
- 不能省略的安全、校验、错误处理、可访问性或测试：
```

优先顺序：

```text
不做不必要内容 -> 复用项目已有能力 -> 使用平台/标准库 -> 使用已安装依赖 -> 清晰一行 -> 最小新增代码
```

不得为了未来可能性新增抽象、包装器、配置项、未使用参数、依赖或大范围重构。

但也不得为了少写而削减安全、权限、数据保护、错误处理、可访问性、用户明确要求或必要测试。

### 不明确时主动询问

遇到以下情况，不要自作主张：

- 用户目标不清楚。
- 输入材料互相冲突。
- 涉及高风险模块或不可逆操作。
- 需要选择技术方案但没有明显最优解。
- 会改变现有数据结构、接口协议、权限、安全、计费或发布流程。
- 实现范围可能明显超出用户原始需求。
- 验收标准不明确。

应先用简短问题向用户确认，或提供 2-3 个可选方案并说明取舍。

### 保留解释

每次调度时都要说明：

- 当前判断是什么。
- 调用了哪个工作流。
- 为什么不是其他工作流。
- 本次会读取或修改哪些文件。
- 预期会输出什么。
- 后续可能进入哪里。

## 标准开发生命周期

开发治理总入口默认按照下面生命周期推进。

不是每个任务都必须完整走完所有阶段，但跳过阶段时必须说明理由。

| 阶段 | 目标 | 默认工作流 | 是否需要用户确认 |
| --- | --- | --- | --- |
| 0. 任务识别 | 判断用户输入属于哪类开发任务 | `developer-kit-workflow.md` | 不一定 |
| 1. 需求理解 | 确认要解决的问题、目标和范围 | `requirement-to-architecture-workflow.md` | 中高风险需要 |
| 2. 是否开发确认 | 判断是否进入实现阶段 | `change-risk-assessment-workflow.md` | 需要 |
| 3. 项目理解 | 理解当前项目结构、运行方式和约束 | `project-understanding-workflow.md` | 不一定 |
| 4. 功能整体规划 | 拆分功能、模块、数据、接口和实现顺序 | `module-boundary-analysis-workflow.md` + `impact-analysis-workflow.md` | 中高风险需要 |
| 5. 契约治理 | 明确数据、API、状态、错误处理和兼容策略 | `data-api-contract-workflow.md` | 涉及数据/API/状态时需要 |
| 6. 安全权限检查 | 明确登录、权限、敏感数据和高风险操作 | `security-permission-workflow.md` | 涉及权限/安全时需要 |
| 7. 规范检查 | 确认项目设计规范、开发规范、测试规范和 AI 协作规则 | `project-understanding-workflow.md` + `implementation-workflow.md` | 中高风险需要 |
| 8. 最小必要变更判断 | 判断是否真的需要做、能否复用、是否过度设计 | `minimal-change-governance-workflow.md` | 进入实现前需要 |
| 9. 任务拆解 | 将整体规划拆成可逐条执行、逐条验证的开发任务列表 | `implementation-workflow.md` | 中高风险需要 |
| 10. 开发准备 | 确认变更范围、风险、验证方式和回滚策略 | `change-risk-assessment-workflow.md` | 高风险需要 |
| 11. 代码实现 | 按任务列表逐条完成代码改动 | `implementation-workflow.md` | 不一定 |
| 12. 测试验证 | 运行测试、补充验证、整理未覆盖风险 | `testing-verification-workflow.md` | 不一定 |
| 13. 文档同步 | 同步 README、接口、配置、使用说明等 | `documentation-sync-workflow.md` | 不一定 |
| 14. 代码评审 | 检查缺陷、回归风险、边界破坏、过度设计和测试缺口 | `code-review-workflow.md` | 不一定 |
| 15. 发布判断 | 判断是否需要发布、回滚和上线检查 | `release-and-rollback-workflow.md` | 发布相关需要 |
| 16. 复盘沉淀 | 沉淀规则、经验、模板或项目规范 | `ai-collaboration-retrospective-workflow.md` | 不一定 |

## 阶段推进规则

### 从需求到开发

当用户给的是需求、想法、PRD 或产品目标时，默认推进链路是：

```text
需求理解
-> 架构影响分析
-> 是否进入开发确认
-> 项目理解
-> 功能整体规划
-> 数据/API/状态契约检查
-> 安全与权限检查
-> 项目规范检查
-> 最小必要变更判断
-> 开发任务拆解
-> 风险和影响范围确认
-> 代码实现
-> 测试验证
-> 文档同步
-> 代码评审
-> 后续发布或复盘
```

如果用户只要求分析，不要擅自进入开发。

如果用户确认“继续开发”，必须先完成项目理解和功能整体规划。

### 从已有项目问题到开发

当用户给的是 bug、报错、性能问题或已有项目问题时，默认推进链路是：

```text
项目理解
-> 问题定位
-> 数据/API/状态契约检查
-> 安全与权限检查
-> 影响范围分析
-> 修复方案
-> 最小必要变更判断
-> 开发任务拆解
-> 风险确认
-> 代码实现
-> 测试验证
-> 代码评审
-> 文档或复盘
```

如果问题原因不明确，先定位，不要直接修。

### 从明确小改动到实现

当用户给的是明确、低风险、小范围改动时，可以轻量执行：

```text
任务识别
-> 快速影响判断
-> 代码实现
-> 最小验证
-> 结果说明
```

但仍需说明为什么可以跳过完整规划。

### 从发布或上线任务开始

当用户要求发布、部署、上线或回滚时，不要直接发布。

默认推进链路是：

```text
当前状态理解
-> 测试验证检查
-> 发布影响范围
-> 回滚策略
-> 上线前确认
-> 发布后验证
```

## 开发前门禁

进入 `implementation-workflow.md` 前，必须满足以下条件：

- 已明确用户目标。
- 新项目或新模块的技术方案已通过问询确认，或已有项目规则明确授权沿用。
- 已明确本次范围和非范围。
- 已理解项目结构或确认已有足够上下文。
- 已检查项目设计规范、开发规范、测试规范和 AI 协作规则。
- 已判断影响模块。
- 已形成实现顺序。
- 已完成最小必要变更判断。
- 已形成开发任务列表，或说明为什么本次可以轻量跳过。
- 已明确验证方式。
- 中高风险任务已提示风险和确认点。

如果不满足，先补对应阶段，不要直接实现。

## 主动询问规则

当问题不明确时，先问用户。

提问要少而关键，优先问会影响方向的问题。

推荐格式：

```text
我现在不能直接进入实现，因为 {原因}。
需要你确认：
1. {关键问题 1}
2. {关键问题 2}

如果你希望我先按默认假设推进，我会按 {默认假设} 处理。
```

可以主动给出默认假设，但必须让用户知道这是推断，不要把推断当事实。

## 执行状态格式

每次执行前或阶段切换时，输出：

```text
当前阶段：{任务识别 / 需求理解 / 项目理解 / 功能整体规划 / 开发准备 / 代码实现 / 测试验证 / 文档同步 / 代码评审 / 发布判断 / 复盘沉淀}
任务判断：{任务类型}
使用工作流：{workflow}
执行方式：{只分析 / 先方案后实现 / 直接实现}
风险等级：{低 / 中 / 高}
是否需要用户确认：{是 / 否}
已完成：{已完成内容}
正在执行：{当前动作}
下一步：{下一阶段或等待确认}
```

进入实现前，输出：

```md
## 开发任务列表

| 序号 | 任务 | 目标 | 影响文件或模块 | 前置依赖 | 验收标准 | 验证方式 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 |  |  |  |  |  |  | 待执行 |
| 2 |  |  |  |  |  |  | 待执行 |
```

执行每条任务时，输出：

```text
当前执行任务：任务 {序号} - {任务名}
本次只改动：{文件或模块}
验证方式：{命令或手动检查}
完成结果：{完成 / 未完成 / 阻塞}
是否进入下一条：{是 / 否，原因}
```

## 任务结束标准

任务结束前必须说明：

- 当前阶段是否完成。
- 是否已经进入或不进入下一阶段。
- 如果停止，停止原因是什么。
- 如果实现了代码，验证结果是什么。
- 如果没有验证，原因是什么。
- 是否需要同步文档。
- 是否需要代码评审。
- 是否需要发布或回滚判断。
- 是否有需要用户确认的遗留问题。

如果这些信息没有说明完整，不应直接宣称任务完成。

## 输入类型判断

### 类型 1：新项目启动

用户要启动一个新项目、搭建工程结构、补充规范或让 AI 协助初始化项目。

使用：

```text
04-workflows/developer/project-bootstrap-workflow.md
```

适合输出：

```text
项目启动检查、基础规范清单、目录建议、协作规则
```

### 类型 2：已有项目接手

用户已经有一个项目，但不知道结构、运行方式、模块职责或当前状态。

使用：

```text
04-workflows/developer/project-understanding-workflow.md
```

适合输出：

```text
项目理解报告、模块地图、运行方式、风险提示
```

### 类型 3：产品需求进入开发

用户给了产品需求、PRD、用户故事或功能想法，希望判断怎么开发。

使用：

```text
04-workflows/developer/requirement-to-architecture-workflow.md
```

适合输出：

```text
架构影响分析、模块影响、实现切入点、待确认问题
```

### 类型 4：模块边界不清楚

用户不确定功能应该放在哪个模块，或担心模块职责被改乱。

使用：

```text
04-workflows/developer/module-boundary-analysis-workflow.md
```

适合输出：

```text
模块职责边界、允许依赖、禁止跨越边界、协作方式
```

### 类型 5：变更风险判断

用户要改一个功能，但不确定风险高低、是否需要确认、是否会破坏现有行为。

使用：

```text
04-workflows/developer/change-risk-assessment-workflow.md
```

适合输出：

```text
风险等级、确认点、保护措施、回滚建议
```

### 类型 6：影响范围分析

用户想知道某个改动会影响哪些文件、模块、接口、数据或流程。

使用：

```text
04-workflows/developer/impact-analysis-workflow.md
```

## 标准执行流程

### 第 1 步：确认输入是否足够

如果用户只给一句模糊任务，先追问或整理成开发输入。

如果用户已经提供需求、文件或代码上下文，先判断任务类型和风险等级。

### 第 2 步：说明调度判断

输出类似：

```text
我判断这次任务属于 {任务类型}。
建议使用 {工作流路径}。
原因是 {选择理由}。
本次执行方式是 {只分析 / 先方案后实现 / 直接实现}。
风险等级是 {低 / 中 / 高}。
本次预计输出 {输出内容}。
后续可能进入 {后续工作流}。
```

### 第 3 步：进入细分工作流

按照对应细分工作流的输入要求、执行步骤、输出结构和质量标准执行。

### 第 4 步：实现或输出

如果任务需要改代码，按仓库现有结构和用户要求执行。

如果任务只需要分析或方案，优先在对话中输出；需要保存时按外部项目输出目录策略保存。

### 第 5 步：验证并评审

生成结果后，使用对应评分表检查。

评分表优先使用：

```text
11-evaluations/output-scorecards/
```

### 第 6 步：判断后续流转

根据输出结果，判断下一步进入：

- 项目理解。
- 架构影响分析。
- 模块边界分析。
- 风险评估。
- 代码实现。
- 测试验收。
- 文档同步。
- 代码评审。
- 发布回滚。
- AI 协作复盘。
- 暂停并沉淀。

## 推荐项目结构

如果需要保存真实开发执行过程，使用真实项目目录：

```text
12-projects/developer/real-cases/{项目名}/
```

如果只是临时开发问答，可以直接引用全局工作流，不一定创建项目。

如果是建设或优化某个开发能力，使用能力建设目录：

```text
12-projects/developer/capability-building/{能力名}/
```

## 外部项目输出目录策略

在外部项目中保存分析、方案或报告时：

1. 用户指定目录优先。
2. 已有文档目录优先。
3. 已有开发文档目录优先。
4. 没有合适目录时创建 `docs/`。

不要默认创建 WorkflowProject 内部目录：

```text
{目标文档目录}/
12-projects/
```

如果任务是代码实现，应优先修改项目真实代码，并在最终回复中说明修改文件、验证结果和剩余风险。

## 使用示例

### 示例 1：从产品需求进入开发

```text
请使用开发治理总入口处理这个任务：
产品希望新增一个导出功能，请判断会影响哪些模块，并给出实现计划。
```

预期调度：

```text
requirement-to-architecture -> 用户确认是否开发 -> project-understanding -> module-boundary-analysis -> impact-analysis -> implementation -> testing-verification -> documentation-sync -> code-review
```

### 示例 2：接手已有项目

```text
请使用开发治理总入口理解当前项目，并告诉我后续开发前应该注意什么。
```

预期调度：

```text
project-understanding-workflow.md
```

下一步根据用户确认进入：

```text
requirement-to-architecture / impact-analysis / implementation
```

### 示例 3：准备改一个高风险模块

```text
我要修改支付流程，请先判断风险和影响范围。
```

预期调度：

```text
change-risk-assessment -> impact-analysis
```

如果确认继续开发，再进入：

```text
module-boundary-analysis -> implementation -> testing-verification -> code-review
```

### 示例 4：完成开发后准备上线

```text
功能已经开发完了，请帮我做上线前检查和回滚准备。
```

预期调度：

```text
testing-verification -> release-and-rollback
```

如果发布后发现协作问题，再进入：

```text
ai-collaboration-retrospective
```

## 质量检查

使用本总入口时检查：

- 是否先判断任务类型。
- 是否说明调度理由。
- 是否选择了正确细分工作流。
- 是否在报错或测试失败时先做问题定位。
- 是否在数据、API 或状态不清时先定义契约。
- 是否在权限、安全或敏感数据相关任务中先做安全检查。
- 是否在跨阶段任务中说明插入、回退和跳过理由。
- 是否判断风险等级。
- 是否明确执行方式。
- 是否没有把单个工作流当成最终结束。
- 是否在实现前完成整体功能规划。
- 是否在实现前检查项目设计规范、开发规范、测试规范和 AI 协作规则。
- 是否在实现前形成开发任务列表。
- 是否逐条实现、逐条验证，而不是一次性大范围修改。
- 是否保护用户已有改动。
- 是否说明读取或修改的文件。
- 是否明确验证方式。
- 是否说明后续流转。
- 是否在不明确时主动询问。
- 是否持续输出执行状态。
- 是否满足任务结束标准。
- 是否使用对应评分表。

## 注意事项

- 本文件是总入口，不是万能开发模板。
- 明确任务类型后，应进入对应细分工作流。
- 如果任务跨多个阶段，可以串联多个工作流，但每一步都要说明当前阶段。
- 如果任务涉及产品目标不清，应先回到产品经理能力补齐需求。
- 如果任务涉及视觉设计，应先交给 UI/设计角色明确设计输入。
