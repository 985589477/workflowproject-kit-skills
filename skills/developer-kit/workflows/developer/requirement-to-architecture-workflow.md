# 需求到架构影响分析工作流

## 目的

当一个产品需求准备进入开发时，帮助 AI 把需求翻译成开发可执行前的架构影响分析。

本工作流重点解决：

1. 需求是否已经足够清楚。
2. 需求会影响哪些页面、模块、接口、数据和状态。
3. 是否需要新增模块，还是应该扩展已有模块。
4. 模块之间如何协作。
5. 哪些地方存在风险，需要先确认再开发。
6. 后续应该进入哪个 developer-kit 工作流。

一句话：

```text
需求到架构影响分析 = 把“想做什么”翻译成“项目哪里要变、怎么变、风险在哪”。
```

## 适用场景

适用于：

- 用户提供产品需求、PRD、用户故事或口头想法。
- 准备在已有项目中开发新功能。
- 需求涉及多个页面、模块、接口、数据或状态。
- 用户不确定这个需求应该改哪里。
- 用户希望 AI 先分析影响范围，再进入实现。

不适用于：

- 项目还没被理解，应先使用 `project-understanding-workflow.md`。
- 新项目还没有基础治理，应先使用 `project-bootstrap-workflow.md`。
- 只是极小的文案、样式或单文件调整。

低风险小改可以轻量使用本工作流。

## 输入要求

至少需要：

- 需求描述。
- 当前项目理解报告，或项目的基本目录和模块信息。

建议同时提供：

- PRD。
- 用户故事。
- 验收标准。
- 当前模块地图。
- 当前接口或数据结构。
- 用户明确不希望改动的范围。

## 执行原则

### 1. 先判断需求清晰度

如果需求目标、用户、场景、成功标准或不做范围不清楚，应先列出待确认问题。

### 2. 先找已有模块，再考虑新增模块

不能因为新需求出现就直接新增模块。新增模块必须有稳定业务概念、独立职责或复用价值。

### 3. 先分析影响，再进入实现

本工作流产出的是架构影响分析，不直接写代码。

### 4. 风险越高，确认越前置

涉及数据结构、权限、登录、支付、迁移、生产配置、跨模块核心链路时，必须先给方案并等待确认。

### 5. 输出必须能被后续工作流继续使用

分析结果应能交给：

```text
module-boundary-analysis-workflow.md
change-risk-assessment-workflow.md
impact-analysis-workflow.md
implementation-workflow.md
```

## 执行步骤

### 第 1 步：需求澄清

识别需求中的关键信息：

```text
目标用户
使用场景
核心目标
触发入口
主流程
异常流程
成功标准
不做范围
约束条件
```

产出：需求清晰度判断和待确认问题。

### 第 2 步：匹配现有项目能力

基于项目理解报告或源码结构，判断需求可能落在哪些区域：

- 页面或路由。
- 组件。
- 业务模块。
- 状态管理。
- API 服务。
- 数据模型。
- 权限或登录。
- 配置或环境。
- 测试。
- 文档。

产出：现有能力匹配表。

### 第 2.5 步：确认技术基线

如果是已有项目，先读取配置、依赖和源码，输出：

```text
主要语言
框架及版本
运行时
包管理器
构建和启动方式
测试工具
```

如果是新项目，或当前项目技术栈不一致，必须通过问询确认技术方案。至少询问目标平台、主要语言、框架、运行环境、构建方式和测试方式。

如果是新模块，必须询问是否沿用当前项目技术栈。没有用户确认前，不得因为 AI 熟悉某种语言或框架就直接生成模块骨架。

### 第 3 步：判断模块变更方式

对每个受影响模块判断：

```text
无需修改
扩展已有能力
调整模块边界
新增模块
拆分模块
废弃旧能力
```

产出：模块变更建议。

### 第 4 步：分析数据和状态影响

判断是否涉及：

- 新增字段。
- 修改字段含义。
- 新增数据实体。
- 数据迁移。
- 缓存。
- 本地状态。
- 全局状态。
- 服务端状态。
- 权限状态。

产出：数据与状态影响分析。

### 第 5 步：分析接口和协作影响

判断是否涉及：

- 新接口。
- 修改接口。
- 删除接口。
- 参数变化。
- 返回结构变化。
- 错误码变化。
- 前后端协作。
- 第三方服务。

产出：接口与协作影响分析。

### 第 6 步：识别风险等级

按以下标准分级：

| 等级 | 判断标准 | 执行策略 |
| --- | --- | --- |
| 低风险 | 单页面、单组件、无数据结构变化 | 可进入实现，简短说明 |
| 中风险 | 单模块功能、局部状态或局部接口变化 | 先确认影响分析，再实现 |
| 高风险 | 跨模块、核心流程、权限、数据结构变化 | 先给方案，等待确认 |
| 危险变更 | 数据迁移、删除数据、生产配置、批量重构 | 必须人工确认 |

产出：风险等级和确认策略。

### 第 7 步：形成架构影响分析报告

报告必须包含：

```text
需求摘要
需求清晰度
待确认问题
影响范围
模块变更建议
数据与状态影响
接口与协作影响
风险等级
建议执行顺序
后续工作流建议
```

产出：架构影响分析报告。

## 与其他 developer-kit 工作流的关系

| 上下游 | 工作流 | 关系 |
| --- | --- | --- |
| 前置 | `project-understanding-workflow.md` | 先理解项目，才能判断需求影响哪里。 |
| 后续 | `module-boundary-analysis-workflow.md` | 当模块职责或新增模块判断不清时使用。 |
| 后续 | `change-risk-assessment-workflow.md` | 当变更风险较高时使用。 |
| 后续 | `impact-analysis-workflow.md` | 当需要更细的文件、接口、测试影响清单时使用。 |
| 后续 | `implementation-workflow.md` | 当需求、影响和风险都清楚后进入实现。 |

## 快速启动话术

```text
请参考 04-workflows/developer/requirement-to-architecture-workflow.md，
基于当前项目理解，把下面这个产品需求转换成架构影响分析报告。

需求：
【粘贴需求】

请不要直接改代码，先输出影响范围、模块变更建议、数据/API/状态影响、风险等级、待确认问题和下一步建议。
```

## 质量要求

- 不能只复述需求，必须说明项目哪里会变。
- 不能跳过需求不清的问题。
- 不能默认新增模块，必须给出判断理由。
- 涉及高风险区域时，必须要求人工确认。
- 输出必须能被后续模块边界、风险评估、影响分析和实现工作流继续使用。
