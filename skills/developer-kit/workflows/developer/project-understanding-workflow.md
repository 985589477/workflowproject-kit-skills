# 已有项目理解工作流

## 目的

在接手一个已经存在的代码项目时，帮助 AI 先建立项目全局理解，再决定如何进入开发。

本工作流重点解决：

1. 避免 AI 没读懂项目就直接改代码。
2. 帮助用户快速知道项目当前是什么、怎么启动、怎么验证。
3. 梳理主要模块、模块边界和模块协作关系。
4. 找出项目中的缺失文档、潜在风险和不确定点。
5. 识别项目设计规范、开发规范、测试规范和 AI 协作规则。
6. 为后续需求开发、重构、测试和交付建立上下文基础。

一句话：

```text
已有项目理解工作流 = 让 AI 先看懂项目，再参与项目。
```

## 适用场景

适用于：

- 用户把 Codex 或 Cursor 接入一个已有项目。
- 项目文件较多，用户自己也不确定整体结构。
- 准备基于已有项目继续开发新需求。
- 项目缺少清晰 README、架构文档或模块说明。
- 用户希望 AI 输出一份“项目理解报告”。
- 项目需要判断是否具备继续开发的治理基础。

不适用于：

- 新项目刚创建，应该优先使用 `project-bootstrap-workflow.md`。
- 用户只问一个局部代码问题，且不需要项目全局理解。
- 用户明确要求只修改一个低风险文件。

这些场景可以轻量使用本工作流，只做局部理解。

## 输入要求

至少需要：

- 项目根目录。
- 用户当前想了解或准备开发的目标。

建议同时提供：

- 项目 README 或说明文档。
- 启动命令、测试命令或部署方式。
- 已知问题或历史背景。
- 用户最担心的区域，例如模块边界、依赖、数据、性能、权限。

## 执行原则

### 1. 先读说明，再读结构

优先阅读：

```text
README.md
AGENTS.md
.cursor/rules/
docs/
package.json / pyproject.toml / Cargo.toml / go.mod 等技术栈入口
```

再阅读源码目录和测试目录。

### 2. 先总结事实，再做推断

输出中要区分：

```text
已确认事实
基于文件结构的推断
仍需用户确认的问题
```

不能把推断当成事实。

### 3. 先识别边界，再建议修改

在没有明确模块职责前，不应直接提出大范围重构建议。

### 4. 尊重本地规则

项目已有的 README、AGENTS.md、Cursor rules、贡献指南、测试规范优先级高于通用 developer-kit。

### 5. 按风险决定理解深度

低风险小改动可以轻量理解；涉及架构、数据、权限、支付、发布、迁移的任务必须完整理解。

## 执行步骤

### 第 1 步：识别项目入口

检查项目根目录中的关键入口：

```text
README.md
AGENTS.md
.cursor/rules/
docs/
package.json / pyproject.toml / Cargo.toml / go.mod / pom.xml 等
src/ 或 app/
tests/ 或 test/
配置文件
环境变量示例
```

产出：项目入口清单。

### 第 1.5 步：扫描规范资产

检查项目中是否存在：

```text
AGENTS.md
AI-WORKFLOW-RULES.md
.cursor/rules/
CONTRIBUTING.md
docs/
docs/development-standard.md
docs/design-system.md
docs/component-guidelines.md
docs/ui-guidelines.md
docs/testing.md
storybook 配置
组件库文档
.editorconfig
.prettierrc
.eslintrc
biome.json
tsconfig.json
ruff.toml
pyproject.toml
```

识别以下规范：

- UI 设计规范。
- 组件规范。
- 交互规范。
- 视觉规范。
- 代码风格。
- 架构约束。
- 目录约定。
- 命名规范。
- 测试规范。
- AI 协作规则。

产出：规范资产清单。

### 第 2 步：判断技术栈和运行方式

识别：

- 主要语言。
- 框架。
- 包管理工具。
- 本地启动方式。
- 构建命令。
- 测试命令。
- 代码质量命令。
- 环境变量或外部依赖。

产出：技术栈与运行方式摘要。

### 第 3 步：梳理目录结构

按职责解释主要目录：

```text
目录
负责什么
不负责什么
主要入口文件
与其他目录的关系
```

产出：目录职责地图。

### 第 4 步：识别核心模块

从代码和文档中提取核心模块：

- 页面或路由模块。
- 业务能力模块。
- 数据访问模块。
- 状态管理模块。
- API 或服务模块。
- 工具和基础设施模块。
- 测试模块。

产出：模块地图。

### 第 5 步：分析模块边界

对每个核心模块说明：

```text
模块职责
对外能力
输入
输出
依赖
被谁调用
不应该承担的职责
常见变更风险
```

产出：模块边界说明。

### 第 6 步：识别模块协作链路

梳理典型链路：

- 用户操作到页面。
- 页面到状态。
- 状态到 API。
- API 到数据。
- 数据回到 UI。
- 异常和加载状态处理。

产出：模块协作链路。

### 第 7 步：识别风险和缺口

重点检查：

- README 是否足够。
- 是否缺少开发规范。
- 是否缺少设计规范、组件规范、交互规范或测试规范。
- 是否缺少模块边界说明。
- 是否缺少测试命令。
- 是否缺少环境变量说明。
- 是否存在高耦合或职责混杂。
- 是否有未记录的关键依赖。
- 是否有危险操作或发布风险。

产出：风险与缺口清单。

### 第 8 步：输出项目理解报告

报告必须包含：

```text
项目一句话定位
技术栈
启动和验证方式
主要目录职责
核心模块地图
模块协作关系
关键风险
缺失文档
后续开发建议
进入开发前需要确认的问题
```

产出：项目理解报告。

## 与其他 developer-kit 工作流的关系

| 上下游 | 工作流 | 关系 |
| --- | --- | --- |
| 前置 | `project-bootstrap-workflow.md` | 新项目先建治理基础，已有项目直接进入理解。 |
| 后续 | `requirement-to-architecture-workflow.md` | 在理解项目后，把产品需求转成架构影响分析。 |
| 后续 | `module-boundary-analysis-workflow.md` | 对边界不清的模块做专项分析。 |
| 后续 | `change-risk-assessment-workflow.md` | 对即将开发的变更做风险分级。 |
| 后续 | `impact-analysis-workflow.md` | 对具体改动做影响范围判断。 |

## 快速启动话术

```text
请参考 04-workflows/developer/project-understanding-workflow.md，
帮我理解当前项目。

请先阅读 README、AGENTS、docs、技术栈入口文件和主要源码目录，
然后输出项目理解报告，包括技术栈、启动方式、目录职责、核心模块、模块边界、风险缺口和下一步建议。
```

## 质量要求

- 必须有文件证据，不能只凭目录名猜测。
- 必须区分事实、推断和待确认问题。
- 必须说明下一步适合进入哪个工作流。
- 必须避免在理解阶段直接大规模修改代码。
- 如果发现项目缺少基础治理文件，应建议回到 `project-bootstrap-workflow.md` 补齐。
