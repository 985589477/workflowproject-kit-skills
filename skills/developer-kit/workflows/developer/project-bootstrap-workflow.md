# 新项目启动治理工作流

## 目的

在一个新代码项目启动时，帮助用户建立适合 AI 协作开发的基础治理结构。

本工作流重点解决：

1. 检查项目是否具备基础说明、开发规范和 AI 协作规则。
2. 判断当前项目缺少哪些开发治理文件。
3. 给 Codex、Cursor 等 AI 工具建立清晰协作入口。
4. 避免新项目一开始就缺少结构、边界和质量标准。
5. 在不过度工程化的前提下，补齐最小可用治理体系。

## 适用场景

适用于：

- 新项目刚创建。
- 用户准备让 Codex 或 Cursor 长期参与开发。
- 项目只有代码脚手架，但缺少协作规范。
- 项目即将进入产品需求开发前，需要先建立治理基础。
- 用户希望 AI 告诉自己需要补哪些项目规范。

不适用于：

- 已经有成熟开发规范的大型项目。
- 一次性脚本或临时实验。
- 用户明确只想快速写一个小 demo。

这些场景可以轻量使用本工作流。

## 输入要求

至少需要：

- 当前项目根目录。
- 项目类型或技术栈线索；如果没有，需要通过问询确认。
- 用户希望使用的 AI 工具，例如 Codex、Cursor、Claude、通用 Agent。

建议同时提供：

- 项目目标。
- 主要用户或业务场景。
- 是否已有产品需求。
- 是否已有技术栈。
- 是否需要前端、后端、全栈或移动端规范。
- 是否希望直接创建文件，还是只输出建议。

如果还没有确定技术栈，不要直接开始搭建。先询问目标平台、主要语言、框架、运行环境、构建方式和测试方式。

## 执行步骤

### 第 1 步：识别项目现状

先检查项目根目录是否存在：

```text
README.md
AGENTS.md
.cursor/rules/
docs/
docs/architecture/
docs/development-standard.md
docs/quality-checklist.md
package.json / pyproject.toml / Cargo.toml / go.mod 等技术栈入口
测试命令
构建命令
环境变量说明
模块目录说明
```

不要在未检查前直接创建文件。

产出：项目现状摘要。

### 第 2 步：判断项目复杂度

按复杂度分级：

| 等级 | 判断标准 | 治理方式 |
| --- | --- | --- |
| 轻量项目 | demo、脚本、一次性验证 | 只补 README 和最小运行说明 |
| 标准项目 | 会持续开发，有明确功能 | 补 README、AGENTS、docs、质量清单 |
| 多模块项目 | 前后端、多个业务模块、多人协作 | 补架构目录、模块地图、模块契约 |
| 高风险项目 | 涉及权限、支付、数据迁移、生产部署 | 补风险规则、发布检查、回滚说明 |

产出：项目复杂度判断。

### 第 3 步：生成缺失规范清单

按优先级列出缺失内容：

必需项：

```text
README.md
AGENTS.md
docs/development-standard.md
docs/quality-checklist.md
```

建议项：

```text
docs/architecture/README.md
docs/architecture/module-map.md
docs/architecture/module-contract-template.md
.cursor/rules/developer-kit.mdc
```

高级项：

```text
docs/decisions/
docs/release-checklist.md
docs/environment.md
docs/dependency-and-tech-debt.md
```

产出：缺失规范清单。

### 第 3.5 步：问询并确认技术方案

在生成工程骨架、安装依赖或创建第一个模块前，必须通过问询确认：

```text
1. 目标平台：网页 / iOS / Android / 桌面端 / 服务端 / 其他？
2. 主要语言：使用什么语言？
3. 框架：是否指定框架和版本？没有的话是否需要我提供方案？
4. 运行环境：浏览器、操作系统、服务器或容器是什么？
5. 构建和包管理：使用什么构建工具和包管理器？
6. 测试：使用什么测试工具，最低验证要求是什么？
7. 是否允许我根据目标提供 2-3 套技术方案供选择？
```

如果用户暂时不知道，先输出候选方案、适用条件、代价和推荐理由，等待用户选择。不能因为用户没有回答，就自行选定语言或框架并开始搭建。

### 第 4 步：给出补齐方案

说明每个建议文件：

- 为什么需要。
- 解决什么问题。
- 是否必须。
- 是否建议现在创建。
- 创建后由谁维护。

产出：项目治理补齐方案。

### 第 5 步：等待人工确认

如果需要创建或修改文件，先让用户确认。

必须确认的情况：

- 技术栈、框架、运行时或测试方案尚未确认。
- 创建多个规范文件。
- 覆盖已有文件。
- 修改已有 README、AGENTS.md 或 Cursor rules。
- 引入新目录结构。
- 为高风险项目添加发布、权限或环境规则。

产出：待确认问题。

### 第 6 步：生成或更新文件

经用户确认后，按项目实际情况生成：

```text
README.md
AGENTS.md
docs/development-standard.md
docs/quality-checklist.md
docs/architecture/README.md
.cursor/rules/developer-kit.mdc
```

不得强制套用 WorkflowProject 内部目录结构。

产出：项目启动治理文件。

### 第 7 步：输出启动治理报告

说明：

- 已检查哪些内容。
- 已创建或建议创建哪些文件。
- 当前项目治理成熟度。
- 后续开发前还需要补什么。
- 下一步建议进入哪个 developer-kit 工作流。

产出：新项目启动治理报告。

## 推荐输出结构

```md
# 新项目启动治理报告

## 项目现状

## 项目复杂度判断

## 已有治理文件

## 缺失治理文件

| 文件 | 必要性 | 用途 | 建议动作 |
| --- | --- | --- | --- |

## 建议补齐方案

## 需要人工确认的问题

## 后续开发建议

## 下一步建议使用的工作流
```

## 推荐补齐文件

### AGENTS.md

用于让 Codex、Cursor、Claude 等 AI 在项目中读取统一协作规则。

应包含：

```text
项目目标
技术栈
启动命令
测试命令
开发原则
危险操作规则
文档同步规则
交付说明规则
```

### docs/development-standard.md

用于记录开发规范。

应包含：

```text
目录结构
模块边界
命名规则
依赖规则
测试要求
代码风格
文档同步要求
```

### docs/quality-checklist.md

用于开发完成后检查。

应包含：

```text
是否跑测试
是否跑构建
是否更新文档
是否说明风险
是否影响核心路径
是否需要人工验收
```

### docs/architecture/README.md

用于描述项目架构入口。

应包含：

```text
主要模块
模块职责
模块交互
数据流
风险区域
后续待补架构文档
```

### .cursor/rules/developer-kit.mdc

用于 Cursor 项目规则。

应包含：

```text
项目本地规则优先
小任务轻量执行
高风险任务先确认
修改前判断影响范围
修改后同步测试和文档
```

## 人工确认点

以下情况必须先问用户：

- 是否允许创建治理文件。
- 是否允许修改已有 README 或 AGENTS.md。
- 是否允许新增 `.cursor/rules/`。
- 是否允许新增 `docs/architecture/`。
- 项目是否需要轻量版还是完整治理版。

## 质量标准

- 先检查现状，再给建议。
- 不覆盖已有规则。
- 不为小项目引入过重结构。
- 明确必需项、建议项和高级项。
- 输出能同时服务 Codex、Cursor 和通用 AI Agent。
- 后续开发者能通过这些文件理解项目目标、启动方式、测试方式和协作规则。
