# 代码评审工作流

## 目的

在代码实现、测试与文档同步之后，帮助 AI 对本次变更进行最终评审，优先发现 bug、风险、边界破坏、漏测和文档不一致。

本工作流重点解决：

1. 实现是否满足需求和验收标准。
2. 是否存在明显 bug 或边界条件遗漏。
3. 是否破坏模块职责、依赖方向或数据状态归属。
4. 测试是否足够，是否存在未验证风险。
5. 文档是否与代码和验证结果一致。
6. 是否建议交付，还是需要继续修正。
7. 是否存在过度设计、不必要依赖、不必要抽象或可删除代码。

一句话：

```text
代码评审 = 在交付前，用挑错视角检查这次变更是否可靠。
```

## 适用场景

适用于：

- 代码实现已经完成。
- 测试与验收已有结果。
- 文档同步已经完成或已判断不需要同步。
- 用户希望 AI 以评审者身份检查变更。
- 准备交付前做最后质量把关。

不适用于：

- 需求尚未实现。
- 只需要写实现方案。
- 用户明确要求继续开发而不是评审。

## 输入要求

至少需要：

- 修改文件或 diff。
- 变更目标。

建议同时提供：

- 实现交付说明。
- 测试与验收报告。
- 文档同步报告。
- 风险评估报告。
- 模块边界分析报告。

## 执行原则

### 1. 发现问题优先

评审输出应先列问题，而不是先总结做了什么。

问题按严重程度排序：

```text
阻塞
高
中
低
建议
```

### 2. 证据明确

每个问题应尽量给出：

```text
文件路径
相关位置
问题描述
影响
建议修复方向
```

### 3. 不重复实现说明

评审不是重新讲一遍实现过程。没有问题时可以简要说明未发现明显问题，并列出剩余风险或测试缺口。

### 4. 不随意扩大评审范围

聚焦本次变更及其影响范围。发现历史问题可以标记为非本次变更风险。

### 5. 区分必须修复和建议优化

不能把风格偏好伪装成阻塞问题。

## 评审维度

### 1. 需求符合度

检查：

- 是否实现了需求目标。
- 是否覆盖验收标准。
- 是否引入不做范围内的内容。
- 是否遗漏异常流程。

### 2. 正确性

检查：

- 逻辑是否正确。
- 边界条件是否覆盖。
- 错误处理是否合理。
- 空值、异常、并发、重复提交等问题是否处理。

### 3. 模块边界

检查：

- 代码是否放在正确模块。
- 是否破坏模块职责。
- 是否出现不该有的依赖方向。
- 是否把业务逻辑塞进通用层或 UI 层。
- 数据和状态归属是否清楚。

### 4. 风险控制

检查：

- 是否遵守风险评估策略。
- 高风险变更是否有确认记录。
- 是否存在未说明的生产、权限、数据或迁移风险。
- 是否有回滚或降级思路。

### 5. 测试覆盖

检查：

- 是否运行必要测试。
- 是否新增或更新测试。
- 是否覆盖核心路径、异常路径和回归范围。
- 未验证内容是否合理说明。

### 6. 文档一致性

检查：

- README、AGENTS、docs、API 或架构文档是否需要同步。
- 文档中的命令、路径、模块名和行为是否与代码一致。
- 未同步文档是否有原因。

### 7. 可维护性

检查：

- 命名是否清楚。
- 结构是否贴合现有模式。
- 是否引入不必要依赖。
- 是否有重复逻辑。
- 是否有临时方案但未标注。

### 8. 最小必要变更

检查：

- 是否存在用户没有要求的功能、配置、选项或扩展点。
- 是否可以复用项目已有 helper、组件、服务或模式。
- 是否可以使用平台能力、标准库或已安装依赖。
- 是否新增了不必要依赖。
- 是否存在可以删除而不影响需求的代码。
- 是否为了少写而削减了安全、校验、错误处理、可访问性或必要测试。

## 执行步骤

### 第 1 步：读取评审输入

读取：

- 变更目标。
- 修改文件或 diff。
- 实现交付说明。
- 测试与验收报告。
- 文档同步报告。

产出：评审范围摘要。

### 第 2 步：检查变更范围

确认：

- 修改是否超出影响范围。
- 是否触碰禁止修改区域。
- 是否遗漏必须修改的文件。
- 是否有无关格式化或重构。

产出：范围检查结论。

### 第 3 步：逐项评审

按评审维度检查：

```text
需求符合度
正确性
模块边界
风险控制
测试覆盖
文档一致性
可维护性
最小必要变更
```

产出：问题清单。

### 第 4 步：判断交付状态

按以下方式判断：

| 状态 | 含义 |
| --- | --- |
| 可交付 | 没有阻塞或高风险问题，验证充分。 |
| 修正后交付 | 有明确问题，但修复范围可控。 |
| 暂不交付 | 存在阻塞、高风险、验证失败或需求未满足。 |
| 需要人工确认 | 风险或产品/架构决策无法由 AI 判断。 |

产出：交付判断。

### 第 5 步：输出代码评审报告

报告必须包含：

```text
总体结论
问题清单
范围检查
测试与验证评价
文档一致性评价
最小必要变更评价
交付判断
后续建议
```

## 快速启动话术

```text
请参考 04-workflows/developer/code-review-workflow.md，
以代码评审者身份检查本次变更。

请优先列出问题，按严重程度排序，并检查需求符合度、正确性、模块边界、风险控制、测试覆盖、文档一致性、可维护性和最小必要变更。

如果没有发现明显问题，也请说明剩余测试缺口和交付风险。
```

## 质量要求

- 评审必须先列问题。
- 问题必须按严重程度排序。
- 必须尽量给出文件路径和影响说明。
- 不得把风格偏好当成阻塞问题。
- 必须说明是否建议交付。
- 没有发现问题时，也必须说明测试缺口或剩余风险。
