# 依赖与技术债治理工作流

## 目的

在项目长期维护中，帮助 AI 判断是否应该新增、升级、替换或移除依赖，并记录临时方案和技术债的偿还计划。

本工作流重点解决：

1. 是否真的需要新增依赖。
2. 新依赖会带来什么成本和风险。
3. 临时方案是否已经被明确标记。
4. 技术债应该什么时候偿还。
5. 依赖升级、替换和移除如何控制风险。

一句话：

```text
依赖与技术债治理 = 防止短期方便变成长期负担。
```

## 适用场景

适用于：

- 准备新增第三方依赖。
- 准备升级、替换或移除依赖。
- 实现中出现临时方案、绕路方案或 TODO。
- 代码评审发现技术债。
- 依赖存在安全、性能、体积、维护或许可证风险。
- 项目需要建立技术债台账。

不适用于：

- 标准库或项目已有依赖的正常使用。
- 无长期影响的小型实现细节。
- 用户明确要求先快速实验，且结果不会进入主线。

## 输入要求

至少需要：

- 依赖或技术债主题。
- 当前变更目标。

建议同时提供：

- 架构决策记录。
- 代码评审报告。
- 依赖清单，例如 `package.json`、`pyproject.toml`、`requirements.txt`、`go.mod`。
- 相关安全、性能、体积或维护约束。
- 可接受的临时方案期限。

## 执行原则

### 1. 新增依赖必须有理由

AI 不应为了少写几行代码就随意引入新依赖。

新增依赖前必须判断：

```text
是否已有依赖可用
是否标准库可解决
是否值得引入长期维护成本
是否影响包体积、性能、安全或许可证
```

### 2. 临时方案必须可追踪

临时方案必须记录：

```text
为什么临时
影响范围
风险
偿还条件
负责人或触发时机
```

### 3. 技术债要能偿还

技术债记录不能只是抱怨，要包含优先级、影响、偿还方案和触发条件。

### 4. 升级和移除依赖必须有验证

依赖升级、替换或移除需要说明兼容性、影响范围、回滚方式和验证命令。

### 5. 高风险依赖要进入 ADR

影响架构、核心路径、安全、部署或长期维护的依赖选择，应进入 `architecture-decision-record-workflow.md`。

## 执行步骤

### 第 1 步：识别治理对象

判断本次属于：

- 新增依赖。
- 升级依赖。
- 替换依赖。
- 移除依赖。
- 临时方案。
- 技术债记录。
- 技术债偿还。

产出：治理对象分类。

### 第 2 步：判断必要性

分析：

- 当前问题是什么。
- 不引入依赖是否能解决。
- 使用已有能力是否能解决。
- 自研成本和依赖成本分别是什么。
- 是否会长期存在。

产出：必要性判断。

### 第 3 步：评估依赖风险

检查：

- 安全风险。
- 许可证风险。
- 维护活跃度。
- 包体积。
- 性能影响。
- 兼容性。
- 学习成本。
- 锁定风险。
- 替换难度。

产出：依赖风险评估。

### 第 4 步：记录技术债

如果存在技术债，记录：

```text
债务描述
产生原因
影响范围
风险等级
短期收益
长期成本
偿还方案
偿还触发条件
最晚处理时机
```

产出：技术债记录。

### 第 5 步：制定治理方案

根据对象输出方案：

| 对象 | 方案重点 |
| --- | --- |
| 新增依赖 | 是否引入、引入理由、替代方案、验证方式。 |
| 升级依赖 | 版本变化、破坏性变更、兼容性验证。 |
| 替换依赖 | 迁移范围、双轨策略、回滚方式。 |
| 移除依赖 | 替代实现、影响范围、清理清单。 |
| 临时方案 | 标记位置、风险、还债条件。 |
| 技术债偿还 | 拆分步骤、验证和回归范围。 |

产出：治理方案。

### 第 6 步：输出治理报告

报告必须包含：

```text
治理对象
必要性判断
风险评估
备选方案
技术债记录
治理方案
验证要求
是否需要 ADR
后续跟踪
```

## 快速启动话术

```text
请参考 04-workflows/developer/dependency-and-tech-debt-workflow.md，
帮我评估这个依赖/技术债是否应该处理。

主题：
【粘贴依赖、临时方案或技术债说明】

请输出必要性判断、备选方案、风险评估、治理方案、验证要求、是否需要 ADR 和后续跟踪建议。
```

## 质量要求

- 新增依赖必须说明必要性和替代方案。
- 临时方案必须记录还债条件。
- 技术债必须有影响范围、优先级和偿还方案。
- 依赖升级、替换、移除必须有验证和回滚思路。
- 高影响依赖选择必须判断是否需要 ADR。
