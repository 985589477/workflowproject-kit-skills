# 发布与回滚治理工作流

## 目的

在项目准备上线或交付时，帮助 AI 梳理发布前检查、发布步骤、回滚方案、上线后观察和异常处理。

本工作流重点解决：

1. 本次变更是否满足发布条件。
2. 发布前必须检查哪些内容。
3. 发布步骤是否清楚、可执行、可中断。
4. 出现问题时如何回滚。
5. 上线后需要观察哪些指标和现象。
6. 发布失败或异常如何记录并复盘。

一句话：

```text
发布与回滚治理 = 上线前知道怎么发，上线后知道怎么退。
```

## 适用场景

适用于：

- 准备发布到测试、预发或生产环境。
- 变更涉及配置、部署、数据、权限、支付、登录或核心流程。
- 需要制定上线步骤和回滚方案。
- 需要记录发布检查和上线后观察。
- 发布失败后需要梳理恢复方案。

不适用于：

- 只在本地实验，不进入任何共享环境。
- 无部署或交付动作的纯文档变更。
- 用户明确要求只做代码实现，不进入发布治理。

## 输入要求

至少需要：

- 发布目标。
- 本次变更摘要。
- 发布环境。

建议同时提供：

- 实现交付说明。
- 测试与验收报告。
- 文档同步报告。
- 环境与配置治理报告。
- 变更风险评估报告。
- 部署命令、CI/CD 说明或发布平台说明。
- 回滚方式或历史发布记录。

## 执行原则

### 1. 生产发布默认高风险

涉及生产环境、用户数据、权限、安全、支付、登录、核心流程的发布，应默认高风险处理。

### 2. 没有回滚方案，不建议发布

如果无法说明如何回滚或恢复，应标记为发布阻塞或需要人工确认。

### 3. 发布步骤必须可执行

发布步骤应明确：

```text
谁执行
在哪里执行
执行什么
预期结果
失败后怎么处理
```

### 4. 发布前必须有验证证据

不能只凭“代码已改完”发布，必须有测试、构建、验收或人工确认记录。

### 5. 上线后必须观察

发布完成后要明确观察窗口、观察指标、异常信号和处理方式。

## 执行步骤

### 第 1 步：确认发布范围

确认：

- 发布内容。
- 发布环境。
- 影响用户。
- 影响模块。
- 是否涉及配置、数据、权限或外部服务。

产出：发布范围摘要。

### 第 2 步：检查发布前条件

检查：

- 代码评审是否通过。
- 测试与验收是否通过。
- 构建是否通过。
- 文档是否同步。
- 配置是否确认。
- 依赖是否确认。
- 是否有未解决阻塞问题。

产出：发布前检查清单。

### 第 3 步：制定发布步骤

说明：

- 发布顺序。
- 执行命令或平台操作。
- 关键检查点。
- 每步预期结果。
- 每步失败处理。

产出：发布步骤。

### 第 4 步：制定回滚方案

说明：

- 回滚触发条件。
- 回滚步骤。
- 回滚所需权限。
- 回滚后验证。
- 无法回滚时的降级或止损方案。

产出：回滚方案。

### 第 5 步：定义上线后观察

说明：

- 观察窗口。
- 观察指标。
- 日志和错误。
- 用户反馈。
- 关键业务路径。
- 异常处理负责人或动作。

产出：上线后观察计划。

### 第 6 步：输出发布与回滚报告

报告必须包含：

```text
发布范围
发布前检查
发布步骤
回滚方案
上线后观察
阻塞问题
是否建议发布
```

```text

发布目标：

请输出发布范围、发布前检查、发布步骤、回滚方案、上线后观察、阻塞问题和是否建议发布。
```

## 质量要求

- 生产发布默认高风险。
- 没有回滚方案时不建议发布。
- 必须说明发布前验证证据。
- 必须说明回滚触发条件和回滚后验证方式。
- 必须说明上线后观察项。
- 阻塞问题不能被隐藏。
