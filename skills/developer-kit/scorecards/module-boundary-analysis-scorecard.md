# 模块边界分析评分表

状态: draft
版本: v1
适用对象: developer-kit 模块边界分析报告

## 适用场景

用于评估 AI 对模块职责、边界、协作和新增模块判断是否足够清晰。

## 评分维度

每项 1 到 5 分。

| 维度 | 评分说明 |
| --- | --- |
| 分析对象 | 是否明确本次分析的模块、能力点或业务链路。 |
| 现有画像 | 是否说明现有模块路径、职责、对外能力、依赖和问题。 |
| 职责归属 | 是否能把每个能力点归属到合适模块，并说明理由。 |
| 新增模块判断 | 是否基于业务概念、生命周期、复用、输入输出、数据状态和测试独立性判断。 |
| 目标边界 | 是否清楚说明模块负责什么、不负责什么、输入、输出和依赖。 |
| 协作方式 | 是否说明模块调用方向、传参、返回、异常、状态和数据持久化。 |
| 风险识别 | 是否识别职责混杂、循环依赖、重复实现、状态多处修改和过度设计。 |
| 后续衔接 | 是否明确进入风险评估、影响分析或实现工作流的条件。 |

总分：40 分。

## 总分判断

```text
36-40 分：模块边界清晰，可以进入后续开发流程。
30-35 分：基本可用，但需要补充依赖方向、状态归属或风险。
22-29 分：边界仍不清楚，不建议直接实现。
21 分及以下：需要重新做模块边界分析。
```

## 评审输出格式

```md
# 模块边界分析评审

## 总体结论

## 分项评分

| 维度 | 分数 | 说明 |
| --- | --- | --- |

## 主要优点

## 主要问题

## 必须补充的问题

## 是否建议进入实现

## 后续建议
```

## 不合格信号

- 没有说明模块不负责什么。
- 没有说明依赖方向。
- 没有说明数据和状态归属。
- 默认新增模块，没有判断依据。
- 把页面逻辑、业务逻辑、数据逻辑混在一个模块中。
- 没有识别循环依赖或重复实现风险。
- 没有后续工作流建议。
