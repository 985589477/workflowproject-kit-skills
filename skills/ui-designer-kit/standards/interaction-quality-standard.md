# 交互质量标准

## 目的

把“好不好用、是否容易操作、视觉是否清楚、流程是否顺畅”转化为产品和 UI 都能执行与验收的规则。

## 交互质量的六个维度

| 维度 | 需要回答的问题 |
| --- | --- |
| 目标 | 用户进入页面后，是否知道要完成什么？ |
| 路径 | 从开始到完成是否有清晰、必要且连续的步骤？ |
| 操作 | 用户是否能看见、点到、按准核心操作？ |
| 反馈 | 用户操作后，是否立即知道发生了什么？ |
| 恢复 | 出错、误操作或数据为空时，是否知道如何继续？ |
| 视觉 | 层级、间距、颜色、字体和组件是否帮助用户理解，而不是制造噪音？ |

## 产品侧要求

产品文档必须描述行为，不强行规定 UI 的具体视觉实现：

- 用户角色和目标。
- 任务入口和前置条件。
- 主路径步骤和关键决策点。
- 每一步的系统行为和用户可见反馈。
- 成功条件和完成状态。
- 失败、取消、返回、重试和恢复路径。
- 空数据、首次使用、权限不足、网络异常和重复提交。
- 核心操作的优先级和不可替代操作。
- 哪些步骤可以合并、默认、延后或取消。

产品不得只写“操作简单”“体验流畅”“页面美观”，必须转成可观察的行为要求。

## UI 侧要求

### 操作区域

- 触控目标必须遵守目标平台规范；未确认平台时，默认按不小于 `44 x 44` 的触控区域规划，并在平台适配文件中给出最终单位和映射。
- iOS、Android、Web 或桌面端使用各自平台单位时，必须写明实际尺寸，不能只写“按钮适当放大”。
- 视觉图标可以小，但可操作热区不能跟着图标一起缩小。
- 图标按钮必须有可理解的可访问名称、提示或等价文字。
- 相邻高风险操作要有足够间距，避免误触；破坏性操作不能只依靠颜色区分。
- 高频操作应位于用户容易触达的位置，并结合单手、横屏、分屏和折叠状态检查。

### 流程和反馈

- 每个核心任务必须有入口、进行中、成功、失败、取消和恢复路径。
- 提交、保存、删除、支付、上传等操作必须防止重复提交，并说明处理中状态。
- 错误提示应靠近问题位置，说明原因和下一步动作。
- 空状态必须说明当前状态、原因和可执行的下一步。
- 不允许出现点击后无反馈、成功后无确认、失败后只能返回重来的流程。
- 每个页面默认应有明确的主要操作，次要操作不能与主要操作争夺层级。

### 视觉质量

- 先建立信息层级，再决定装饰；装饰不能压过主要任务。
- 字号、字重、颜色、间距、圆角和阴影必须来自设计令牌或明确的局部规则。
- 不使用过小字号、过低对比度、过密操作区或仅靠颜色表达状态。
- 组件在同一任务流中保持名称、位置、反馈和行为一致。
- “好看”必须拆解为可评审项：层级、对齐、节奏、对比、密度、一致性和品牌符合度。

## 交互问题严重程度

| 等级 | 判断 | 处理 |
| --- | --- | --- |
| 阻塞 | 用户无法完成核心任务，或误操作会造成不可逆损失 | 必须修复，不得交付 |
| 高风险 | 用户容易点错、看不懂、重复提交或无法恢复 | 交付前必须修复或获得明确豁免 |
| 中风险 | 增加理解成本、步骤或视觉噪音 | 优先修复，记录是否延期 |
| 低风险 | 不影响完成任务的一致性或细节问题 | 可进入后续优化清单 |

## 最低交互验收

- [ ] 用户能说出当前页面目标。
- [ ] 用户能找到核心操作。
- [ ] 核心操作区域符合目标平台规范。
- [ ] 点击、提交、加载、成功、失败和空状态都有反馈。
- [ ] 错误后有明确恢复动作。
- [ ] 主路径没有无价值的重复步骤。
- [ ] 视觉层级能区分主要、次要和危险操作。
- [ ] 移动端、平板、横屏、分屏或折叠状态没有明显操作障碍。
