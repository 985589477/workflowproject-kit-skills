# 门禁 07：工作量单位

**触发**：任何给用户的工作量估计、阶段划分、排期、"大概要多久"。

**为什么**：AI 协作下的工作量与传统估算是**两套量纲**。用"天/周"会让用户无法判断，
而且**严重高估**（AI 的实际产出速度与日历时间脱钩）。原 kit 全仓 grep
`会话数|工作量单位` = **0 命中**，没有任何指导。

**我实测踩到的**：我第一版方案给出「44–66 天」。用户直接质疑："为什么会有按天计算的？
AI 不是很快吗？"——那次质疑是对的：**那个数字既不可验证，也无法用来做决策**。

---

## 必须产出的格式

```markdown
| 阶段 | 会话数 | 交付物 | 必须等你的检查点 |
|---|---|---|---|
| P0 安全网 | 1–2 | 守卫测试 + 基线报告 | 无 |
| P2 设计系统 | 3–5 | 外壳 + token + 原语 | **有：视觉够不够好** |
| P3 行情模块 | 2–3 | 模块成形 | 无 |
```

**给区间（1–2），不给单点。** 单点数字是假精度。

## 三个必须区分的量

| 量 | 说明 |
|---|---|
| **会话数** | AI 能连续干活的单位。这是主单位 |
| **必须等人的检查点数** | 每个检查点会**打断流程**，实际耗时取决于用户 —— 必须单列 |
| **不可压缩的人工动作** | 你手工要做的（点按钮、跑客户端、肉眼验收、决策） |

**总时长 ≈ 会话数 × 单会话时长 + 人工检查点的等待 + 不可压缩人工动作。**
把三者混成一个"天数"是错的。

## 检查方式

1. 有没有出现"天/周"？→ 除非用户明确要求日历时间，否则改写为会话数。
2. 有没有单列"必须等人的检查点数"？→ 没有就不合格（这是最容易被忽略的隐藏成本）。
3. 估计里有没有**说明估算依据**？（例如"按每个模块 700–1,600 行组件 + 现有测试覆盖度"）
   凭感觉给的区间没有意义。
4. 有没有标出**不确定性来源**？（哪一步的规模最不清楚 —— 通常是需要先审计才知道的部分。）

## 一条实践建议

**先给"探测型第一步"的估计，而不是全程估计。** 例如：

> 「第 1 步（审计与基线）1–2 会话，做完我能给出后面各阶段的可靠估计。
> 现在直接给全程数字会是猜的。」

这比一个漂亮但不可信的全程排期有用得多。

## 反例

| 反例 | 后果 |
|---|---|
| "大约 2 个月" | 用户无法决策，且大概率高估 |
| 只给总会话数，不列检查点 | 隐藏了"要等你"的成本 |
| 给单点数字（"5 个会话"） | 假精度，一旦超了就失去信任 |
| 把不可压缩的人工动作算进 AI 会话 | 数字虚高 |
| 全程排期在审计之前给出 | 建立在猜测上 |
