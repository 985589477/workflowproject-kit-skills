# 门禁 03：以代码为准

**触发**：每当你要**依据项目文档**（架构文档、设计规范、README、PROJECT_CONTEXT、注释里的
流程图）做决定或下结论时。**包括**你准备把这些文档写进方案、写进交接、或作为"现状"汇报给用户时。

**为什么**：kit 的第一条生命周期规则是"先读取项目已有的架构、模块、设计规范"。
如果照做而**不校验**，你会**信任错的文档**，然后把错误结论写进方案。

在 StockTools 里，`docs/` 有 **8 处自相矛盾**，其中三条直接会造成错误决策：

| 文档说 | 实际 | 造成的错误 |
|---|---|---|
| `ARCHITECTURE.md:206` / `PROJECT_CONTEXT.md:251`：任务冲突时返回 **409** | 全仓**没有任何 409**。真实行为是 **200 + 静默 attach**（两个下载任务写同一标的） | 按文档设计前端会去 catch 409，实际永远不触发 |
| `ARCHITECTURE.md:196` 把 `buildDecisionSectorGroups` 列为**关键函数** | 它是**死代码**（零调用） | 照着它做重构会把死代码当核心 |
| 某 `:root` 被"100% 覆盖" | **不是**：它独有 `color-scheme` 和 `font-family`，直接删会**丢掉全局字体与配色** | 删了就是全局样式崩 |
| 审计报告称"140 处 hex 是 token 值被手打" | 实测**只有 36 处** | 按 140 估工作量，且会把"离板值"当成机械替换（实际是视觉变更） |

**注意**：这些错误全都在**"权威文档"里**，不在代码里。文档是**第二份错误的事实来源**。

---

## 必须产出

```markdown
## 文档一致性核查（{日期}）
| 文档断言 | 位置 | 代码证据 | 结论 |
|---|---|---|---|
| 冲突任务返回 409 | ARCHITECTURE.md:206 | `grep -rn 409 src/` → 0 命中 | ❌ 文档错，实际 200+静默 attach |
```

**每条被引用的文档断言都必须有一行代码证据**（命令 + 结果，或 `文件:行`）。
不一致的：**登记 + 修正文档**（或明确标注"已知过期"），不要沉默地绕过。

## 检查方式

1. 把结论里所有"因为文档说…所以…"的句子挑出来，逐条给出代码证据。
2. 数字类断言（"有 N 处"、"占比 X%"）**必须自己数一遍**。
   我这轮数了，发现审计报告有 2 个夸大的数字。
3. 文档里的**行号**尤其可疑：代码一改，行号全错位。

## 硬性规则

- **代码是事实来源，文档是索引。** 冲突时以代码为准，并修正文档。
- **不要把文档的字面内容当成"现状"汇报给用户**，除非你验证过。
- 交接文档里的"现状"段，必须是你**自己验证过**的，不是抄文档的。
- 反过来也成立：**不要因为文档过期就无视它的意图**。文档会告诉你"为什么这样设计"，
  那是代码里读不出来的信息。区分**意图**（可能有价值）和**断言**（必须验证）。

## 反例

| 反例 | 后果 |
|---|---|
| 把 `docs/` 的模块图当架构现状 | 方案基于不存在的模块划分 |
| 引用文档里的行号 | 早已错位 |
| 用户问"现在是怎么工作的"，你复述文档 | 你成了错误信息的放大器 |
| 发现不一致但不登记 | 下一个人再踩一遍 |
