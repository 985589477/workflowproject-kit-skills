# 门禁 06：环境能力探测

**触发**：第一次要在这个环境跑任何命令时（装依赖、跑测试、构建、起服务）。
**以及**：任何"应该能跑"的命令失败之后 —— 先怀疑环境能力，再怀疑代码。

**为什么**：真实环境的能力边界与"标准做法"经常不一致。如果不先探测就照着教科书操作，
你会浪费大量时间在**环境不允许**的动作上，而且失败信息看起来像代码问题。

原 kit 有 `environment-config-governance-workflow.md`，但它讲的是**配置治理**（12-factor 那类），
**不是"这台机器到底能做什么"**。

**我实测踩到的**：

| 现象 | 真实原因 | 代价 |
|---|---|---|
| `pip install httpx2` 失败 | 沙箱禁止写 `~/.local` 和 conda site-packages | 试了多次才确认不可行，只能换验证方式 |
| `npm install` EPERM | `~/.npm/_cacache` 属 root | 若用 `sudo chown` 会污染全局环境（错解） |
| `timeout 10 python ...` 报 command not found | macOS 没有 `timeout`（要 `gtimeout`） | 脚本写错 |
| `vite build` 成功但类型全错 | **`vite build` 默认只转译不做类型检查** | 差点以为类型没问题 |
| `python3 -m pytest` 报找不到 pytest | 系统 python 与项目 env 不同 | 命令必须写全路径 |

---

## 必须产出（写进项目 `AGENTS.md`）

```markdown
## 环境与验证命令（均已实测）
- Python：{绝对路径}（不是 `python3`）
- 装依赖：{命令} / 受限：{装不了什么，替代做法}
- 跑测试：{命令} → 期望 {N} passed
- 类型检查：{命令} → 期望 0 错误（注意：{哪个命令不做类型检查}）
- 构建：{命令}
- 起服务：{命令} → {URL}
- 已知环境限制：{列表 + 各自的替代做法}
```

**每条都必须真跑过并记录真实退出码。** 从文档抄的不算。

## 检查方式

1. 新开一个 shell，逐条粘贴执行 —— **全部能跑通**才算探测完成。
2. 记录**失败**的尝试和替代做法，这比成功的清单更有价值。
3. 特别确认：**类型检查是否被构建命令覆盖**（很常见的不一致）。
4. 确认**测试是否隔离**：测试跑完后，真实数据/真实库有没有被改动？
   （我这轮踩到：测试 fixture 定义在某个测试文件里，其他文件**不继承**它，
   于是路径解析到了**真实的数据库**。修法是把隔离 fixture 放进 `conftest.py`。）

## 硬性规则

- **验证命令必须写进 `AGENTS.md`**，不能只存在于对话里。
- 命令用**绝对路径**或项目内相对路径，不依赖 shell 的 PATH 状态。
- 环境限制要做**显式降级**，不是绕过：降级要说明"因此这个验证项的覆盖度降低了"，让用户知道。
- 测试**绝不允许**碰到真实用户数据。做一次"跑测试前后对真实库做校验和"的确认。

## 反例

| 反例 | 后果 |
|---|---|
| 命令写在对话里 | 换会话就丢，下次重新踩 |
| 用 `sudo` 治权限问题 | 污染全局环境，问题更大 |
| 假设构建命令会做类型检查 | 类型错误静默通过 |
| 测试直接读写真实数据库 | 真实数据被测试污染（不可恢复） |
| 装不上依赖就绕过验证 | 覆盖度悄悄下降，没人知道 |
