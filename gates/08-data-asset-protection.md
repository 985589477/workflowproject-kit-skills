# 门禁 08：数据资产保护

**触发**：仓库里含**数据库、二进制、大文件、或 Git LFS 跟踪的对象**，且你要改动它们
（或改动会写它们的代码）。

**为什么**：代码可以 `git checkout` 回来，**数据通常不行**——尤其是：

- 数据库被直接提交进 git（二进制，无法 diff、无法合并、损坏后不可恢复）
- 数据是 Git LFS 对象（未 pull 时是**指针文本**，看起来像文件，实际不是）
- 数据只在本地存在，没有任何备份

**我实测遇到的**（StockTools）：

| 事实 | 风险 |
|---|---|
| `market/data/app.db` 是 Git LFS 跟踪的 **786MB SQLite** | 未 pull 时是 **134 字节指针文本**；直接启动 → `DatabaseError: file is not a database`，**行情模块全部 500** |
| `industry.db` 2.1MB、用户库 197KB 是**普通 git 二进制** | 一旦被写坏，git 里没有可用的历史版本 |
| `db.py` 有两处**手写的 `DROP TABLE` 重建**（221-257 / 339-375） | 从未被测试执行过；一旦触发会**丢表** |
| 用户库 `auth/users.json` 提交了**明文密码** | 仓库一旦公开即泄露 |

---

## 必须产出

```markdown
## 数据资产清单
| 资产 | 路径 | 大小 | 形态 | 是否 LFS | 备份位置 |
|---|---|---|---|---|---|
| 行情库 | stocktools-data/market/data/app.db | 786MB | SQLite | 是 | {仓库外路径} |

## 迁移策略
- 只做加法（加列/加索引/加表），不做破坏性重建
- 现有 DROP TABLE 重建路径：{保留 / 加确认 / 移除}
- 备份可恢复性：已实测恢复到 {临时路径} 并 {校验命令} = ok
```

## 检查方式

1. **确认文件形态**：`file {path}`。LFS 指针是文本，SQLite 是 `SQLite 3.x database`。
   **不要靠大小判断**（指针也可能很小，但真实库也可能很小）。
2. **备份必须在仓库外**，且**实测过可恢复**（恢复到一个临时路径，跑完整性校验）。
   ```bash
   sqlite3 "$BAK" 'PRAGMA integrity_check;'   # 或 quick_check（大库快得多）
   ```
3. **跑测试前后对真实数据做校验和**，确认测试没有污染真实数据。
4. **改动 schema 前**，先确认是否有未经测试执行的破坏性路径（`DROP TABLE` / `DELETE FROM`
   无 WHERE / `rmtree`）。

## 硬性规则

- **只做加法迁移**。破坏性重建必须：① 有备份 ② 实测过恢复 ③ 明确告知用户会丢什么。
- **大文件不要进 git 历史**。已经进了的，不要"顺手清理"——重写历史风险远大于收益，
  要单独作为一个有明确确认的动作。
- **凭证不进仓库**。发现明文密码 → 报告用户（改仓库可见性、轮换凭证），
  但**不要**自作主张改认证逻辑。
- **测试绝不碰真实数据**（与门禁 06 联动）。

## 反例

| 反例 | 后果 |
|---|---|
| 用 `file` 之外的方式判断形态 | 把 LFS 指针当数据库，报错信息误导 |
| 备份到仓库内 | `git clean` 一起删掉 |
| 只在本地复制一份当备份 | 同盘故障一起丢 |
| 直接跑未经测试的迁移脚本 | 丢表，不可恢复 |
| "顺手"把大文件从 git 历史里清掉 | 需要 force push，风险极高 |
